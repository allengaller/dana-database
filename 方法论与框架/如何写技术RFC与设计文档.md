# 如何写技术RFC与设计文档

技术 RFC（Request for Comments）和设计文档（Design Doc）是工程师最被低估的杠杆工具之一。一份好的设计文档可以在写一行代码之前发现架构缺陷，可以在团队之间建立共识，可以在三年后帮助新人理解「为什么系统是这样的」。

但大多数工程师要么不写设计文档（「代码就是文档」），要么写出来的文档没人看（「写了 30 页，只有我自己读了」）。本文提供一套经过 Google、Uber、Rust 社区、React 社区验证的 RFC/设计文档方法论，帮助你写出**有人读、有决策、能落地**的技术文档。

---

## 为什么需要这个方法论

### 不写设计文档的代价

| 场景 | 没有设计文档 | 有设计文档 |
|------|------------|-----------|
| 新人入职 | 花 3 个月读代码猜「为什么这样设计」 | 花 1 周读文档理解设计意图和约束 |
| 架构变更 | 「这个模块谁也不敢动，因为没人知道为什么是这样」 | 文档记录了约束和权衡，可以安全地评估变更影响 |
| 跨团队协作 | 反复开会解释接口设计，每次都有不同理解 | 一份文档作为 single source of truth |
| 技术债务 | 不知道哪些是「有意为之」哪些是「临时方案」 | 明确标记 trade-off 和 TODO |
| 决策追溯 | 「为什么用 MongoDB 不用 PostgreSQL？」——没人记得 | ADR/RFC 记录了上下文、备选方案和决策理由 |

### 写设计文档的时机

不是所有变更都需要设计文档。判断标准：

**需要设计文档的信号**：
- 变更影响 2 个以上团队或 3 个以上服务
- 变更不可逆或回滚代价极高（数据库 schema 变更、API 破坏性变更）
- 存在 2 个以上合理的实现方案，需要明确选择
- 变更涉及新的外部依赖或技术选型
- 项目预计超过 2 周工时
- 需要跨团队评审或获得 buy-in

**不需要设计文档的信号**：
- 单模块内的 bug fix
- 明确的重构（不改变行为）
- 已有明确 pattern 的功能扩展
- 预计 1-2 天完成的小变更

**核心原则**：设计文档的价值与决策的「不可逆性」和「影响范围」成正比。参见 [[技术决策框架]] 中的 Type 1 / Type 2 决策分类——Type 1 决策必须有文档，Type 2 决策可以口头沟通。

## 核心框架

### 框架一：Google 风格设计文档（Design Doc）

Google 的设计文档文化是业界最成熟的。其核心结构：

```markdown
# [项目/功能名称] 设计文档

作者：[你的名字]
审阅者：[需要 review 的人]
状态：Draft / In Review / Approved / Implemented
最后更新：[日期]

## 1. 概述（Overview）
[2-3 句话概括这个设计要解决什么问题、核心方案是什么]

## 2. 背景与动机（Context & Motivation）
[为什么需要做这件事？当前系统有什么问题？业务需求是什么？]

## 3. 目标与非目标（Goals & Non-Goals）
### 目标
- [这个设计要达成什么]
### 非目标
- [明确不做什么，避免范围蔓延]

## 4. 设计方案（Design）
### 4.1 整体架构
[系统架构图、组件关系、数据流]

### 4.2 详细设计
[核心算法、数据结构、API 设计、数据库 schema]

### 4.3 备选方案（Alternatives Considered）
[考虑过但没选的方案，以及为什么不选]

## 5. 跨领域关注点（Cross-cutting Concerns）
- 安全性：[安全影响和对策]
- 可观测性：[日志、监控、告警]
- 兼容性：[向后兼容、迁移策略]
- 性能：[性能影响和基准]

## 6. 发布计划（Rollout Plan）
[分阶段发布策略、feature flag、回滚方案]

## 7. 开放问题（Open Questions）
[尚未决定的问题，需要进一步讨论]
```

**Google 设计文档的关键原则**：

1. **先写概述，最后写概述**：先写完整文档，最后回头精炼概述。概述是给忙碌 的人看的——如果他们只读 3 句话，这 3 句话必须传达核心信息。

2. **非目标和目标一样重要**：明确写出「不做什么」可以防止范围蔓延（scope creep），也可以防止审阅者提出超出范围的建议。

3. **备选方案是灵魂**：没有备选方案的设计文档只是「实现计划」，不是「设计决策」。审阅者最想看的是「你考虑了什么、为什么没选」。

4. **图表胜过千言**：一张清晰的架构图比 3 页文字描述更有效。使用 Mermaid、draw.io 或 Excalidraw。

### 框架二：Rust RFC 流程

Rust 语言的 RFC 流程是开源社区中最严格、最成功的设计决策流程之一。自 2014 年以来，Rust 通过 RFC 流程做出了数百个语言设计决策。

**Rust RFC 模板**：

```markdown
# RFC: [功能名称]

- Feature Name: [用于跟踪的标识符]
- Start Date: [日期]
- RFC PR: [链接]
- Rust Issue: [链接]

## Summary
[一段话概括提案]

## Motivation
[为什么需要这个功能？解决什么问题？]

## Guide-level explanation
[假设读者是 Rust 用户，用教程式语言解释这个功能怎么用]

## Reference-level explanation
[精确的技术规范，足以让编译器开发者实现]

## Drawbacks
[为什么不应该做这个？有什么代价？]

## Rationale and alternatives
- 为什么这个设计是最好的？
- 考虑了哪些替代方案？
- 如果不做这个会怎样？

## Prior art
[其他语言/系统中类似的设计，它们的经验教训]

## Unresolved questions
[需要在实现过程中回答的问题]

## Future possibilities
[这个 RFC 可能开启的未来方向]
```

**Rust RFC 流程的关键洞见**：

1. **Drawbacks 是必填项**：强制作者思考「为什么不应该做这个」。这避免了「提案偏见」——人们倾向于只看到好处。

2. **Guide-level 和 Reference-level 分离**：同一件事用两种方式解释——一种给使用者（直觉性），一种给实现者（精确性）。这确保了设计不仅技术上正确，而且对用户友好。

3. **Prior art 是必修课**：要求作者调研其他语言/系统的类似设计。这避免了「重新发明轮子」和「重复别人的错误」。

4. **公开讨论**：RFC 在 GitHub 上公开讨论，任何人都可以评论。这利用了「林纳斯定律」——足够多的眼睛，所有 bug 都是浅的。

### 框架三：Uber 的 RFC 实践

Uber 在 2020 年公开分享了他们的 RFC 流程。与 Google 和 Rust 不同，Uber 的 RFC 更侧重于**工程执行**而非**语言设计**。

**Uber RFC 的核心特征**：

1. **一页纸原则**：核心设计必须能在一页纸内说清楚。附录可以很长，但决策本身必须简洁。

2. **强制审阅者列表**：每个 RFC 必须指定 3-5 个审阅者，包括：
   - 领域专家（技术正确性）
   - 受影响的团队代表（兼容性）
   - 一个「外行」（可读性测试——如果外行看不懂，说明写得不清楚）

3. **时间盒**：RFC 有明确的评论期（通常 5 个工作日）。到期后，如果没有 blocking 意见，RFC 自动通过。这避免了「永远在 review」的瘫痪。

4. **决策记录**：RFC 通过后，所有评论和回应都保留在文档中。三年后回看，你不仅知道「做了什么决策」，还知道「为什么这样决策」以及「当时考虑了什么」。

### 框架四：React RFC 流程

React 团队在 2019 年引入了 RFC 流程（reactjs/rfcs），用于讨论 React 的重大变更。

**React RFC 的独特之处**：

1. **Teach-first 结构**：RFC 必须先解释「如何向用户教这个功能」。如果一个功能难以教学，那它可能设计得不好。

2. **详细示例驱动**：每个 RFC 必须包含多个代码示例——基本用法、边界情况、与现有功能的交互。

3. **迁移路径优先**：对于破坏性变更，RFC 必须详细说明迁移路径——现有代码如何升级？能否自动化？

## 实战案例

### 案例一：Google 的 Spanner 设计文档

Google 的 Spanner（全球分布式数据库）设计文档是技术写作的典范。

**为什么成功**：
- 清晰的「TrueTime API」概念——用一个简洁的抽象解释了整个系统的核心创新
- 明确的 CAP 定理定位——「我们选择 CP，但通过 TrueTime 最小化不可用窗口」
- 详细的性能数据——不是「很快」，而是「99.9% 的读取在 10ms 内完成」
- 备选方案讨论——为什么不用 Paxos 的变体、为什么不用最终一致性

**可学习的点**：
- 用一个核心抽象（TrueTime）统一整个设计叙事
- 用数据说话，不用形容词
- 明确说出「我们选择了什么、放弃了什么」

### 案例二：Rust 的 async/await RFC（RFC 2394）

Rust 的 async/await 设计历时 3 年（2017-2019），经历了多轮 RFC 和大量社区讨论。

**为什么成功**：
- 分阶段设计：先确定语法（RFC 2394），再确定 Future trait（RFC 2592），再确定生态兼容
- 大量 prior art 分析：C# 的 async/await、JavaScript 的 Promise、Scala 的 Future
- 明确的「不做什么」：不在第一版中支持 async trait（留到未来）
- 社区压力测试：数百个 GitHub 评论暴露了大量边界情况

**可学习的点**：
- 大设计可以拆成多个小 RFC，降低每次决策的认知负担
- 公开讨论虽然慢，但产出的设计更健壮
- 「不做什么」的明确声明防止了设计膨胀

### 案例三：一个失败的设计文档（反面教材）

某中型 SaaS 公司的「微服务拆分」设计文档：

**问题**：
- 没有「为什么」：直接跳入「我们要把单体拆成 12 个微服务」，没有解释当前单体的具体痛点
- 没有备选方案：没有考虑「模块化单体」「先拆 2-3 个最痛的模块」等渐进方案
- 没有非目标：没有说明「哪些模块不拆」，导致范围不断扩大
- 没有迁移计划：没有说明如何从单体渐进迁移到微服务，暗示「大爆炸切换」
- 30 页但缺乏关键信息：大量篇幅描述每个微服务的 CRUD 接口，但没有讨论分布式事务、数据一致性、服务发现等核心挑战

**结果**：文档被 CTO 打回重写，项目延迟 2 个月。最终采用了渐进拆分方案（先拆最痛的 2 个模块），而非原计划的 12 个微服务大爆炸。

**教训**：设计文档的价值不在于长度，在于**决策质量**。一份 3 页但清晰说明了「为什么、做什么、不做什么、怎么迁移」的文档，远胜于 30 页的接口列表。

## 常见错误

### 错误一：把设计文档写成实现计划

**表现**：文档全是「第一步做 X，第二步做 Y，第三步做 Z」，没有「为什么选择这个方案」「考虑了什么替代方案」。

**修正**：设计文档的核心是**决策和权衡**，不是任务列表。实现步骤可以放在附录或单独的 task breakdown 中。

### 错误二：写完才给人看

**表现**：花两周写了一份 20 页的文档，发给团队后发现方向完全错了。

**修正**：**早期、频繁地分享**。在写了概述和核心设计（约 1-2 页）时就发给 1-2 个信任的同事，获取方向性反馈。然后再展开详细设计。

### 错误三：忽略「非目标」

**表现**：文档只说「做什么」，不说「不做什么」。结果审阅者不断提出超出范围的建议，作者疲于回应。

**修正**：在文档开头明确列出非目标。例如：「本设计不处理多租户隔离问题，这将在后续 RFC 中讨论。」

### 错误四：过度设计文档

**表现**：一个 3 天的功能写了 15 页设计文档，包含 5 种备选方案的详细分析。

**修正**：文档的详细程度应该与决策的重要性和不可逆性成正比。小变更用 1 页 ADR 即可，大系统才需要完整的设计文档。

### 错误五：没有「开放问题」部分

**表现**：文档假装所有问题都已经解决了。结果实现过程中发现大量未预见的挑战。

**修正**：诚实地列出「尚未决定的问题」。这不是弱点，而是成熟度的标志——说明你知道自己不知道什么。

### 错误六：文档写完就过期

**表现**：设计文档在 Confluence 上躺了三年，系统已经面目全非，文档完全失真。

**修正**：
- 在文档头部标记状态（Draft / Approved / Implemented / Deprecated）
- 重大变更时更新文档（或写新的 ADR 引用旧文档）
- 定期（每季度）清理过期文档

## 工具与模板

### 推荐工具链

| 用途 | 工具 | 说明 |
|------|------|------|
| 文档存储 | Notion / Confluence / Google Docs | 支持协作评论、版本历史 |
| 开源 RFC | GitHub + Markdown | Rust/React 模式，PR 即讨论 |
| 架构图 | Mermaid / Excalidraw / draw.io | Mermaid 可嵌入 Markdown，版本可控 |
| ADR 管理 | adr-tools / MADR 模板 | 轻量级决策记录 |
| 文档即代码 | docs-as-code（Markdown + Git） | 适合技术团队，支持 PR review |

### 轻量级 ADR 模板（适合日常决策）

```markdown
# ADR-[编号]: [决策标题]

日期：[YYYY-MM-DD]
状态：Proposed / Accepted / Deprecated / Superseded by ADR-[X]

## 上下文
[什么情况下需要做这个决策？1-3 句话]

## 决策
[我们决定做什么？1-2 句话]

## 备选方案
- 方案 A：[描述] → 不选因为 [原因]
- 方案 B：[描述] → 不选因为 [原因]

## 后果
- 正面：[好处]
- 负面：[代价]
- 风险：[可能出什么问题]
```

### 完整设计文档检查清单

在提交设计文档审阅前，用以下清单自检：

- [ ] 概述能在 30 秒内让读者理解核心设计
- [ ] 动机部分解释了「为什么现在需要做这个」
- [ ] 目标和非目标都明确列出
- [ ] 至少考虑了 2 个备选方案并解释了选择理由
- [ ] 有架构图或数据流图
- [ ] 讨论了安全性、可观测性、兼容性
- [ ] 有明确的发布/迁移计划
- [ ] 列出了开放问题
- [ ] 文档长度与决策重要性匹配（不过度也不欠缺）
- [ ] 已请 1-2 人预读并确认方向正确

### 设计文档审阅指南（给审阅者）

作为审阅者，你应该关注：

1. **问题定义是否清晰**：作者是否真正理解了要解决的问题？
2. **约束是否完整**：有没有遗漏的重要约束（性能、安全、兼容性）？
3. **备选方案是否充分**：是否真的考虑了其他方案，还是走过场？
4. **权衡是否诚实**：作者是否承认了方案的缺点？
5. **迁移是否可行**：从现状到目标的路径是否清晰？
6. **开放问题是否合理**：有没有被错误地标记为「开放」的已解决问题？

**不要**：
- 纠结格式和拼写（这是作者的事）
- 提出超出非目标范围的建议
- 用「我觉得应该用 X 技术」替代「在 Y 约束下，X 技术比 Z 技术更合适因为...」

## 从设计文档到技术影响力

设计文档不仅是内部工具，也是建立技术影响力的杠杆。参见 [[写作与分享的杠杆]]：

- **内部**：好的设计文档让你在组织中建立「技术判断力」的声誉
- **外部**：将设计文档（脱敏后）发布为博客/演讲，是建立技术品牌的高效方式
- **长期**：设计文档是「可复用的思考」——同样的分析框架可以应用于未来的决策

许多技术领袖的影响力起点就是一份出色的设计文档：
- [[Martin Fowler]] 的很多文章最初就是内部设计文档的公开版
- Rust 的 RFC 作者很多后来成为了 Rust 核心团队
- Google 的 Design Docs 文化培养了一批优秀的系统设计师
