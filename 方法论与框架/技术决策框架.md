# 技术决策框架：从直觉到结构化的决策方法论

> 工程师每天要做无数决策：用什么数据库？要不要拆微服务？自建还是买现成的？
> 大多数决策靠直觉就够了，但**少数关键决策会决定项目未来 3-5 年的走向**。
> 区分这两类决策，并对关键决策使用结构化框架，是高级工程师和初级工程师的分水岭。

---

## 什么时候需要结构化决策？

### 直觉 vs 结构化：不是非此即彼

经验丰富的工程师有大量「模式识别」式的直觉——看到一个问题，脑中立刻浮现解决方案。这种直觉是宝贵的，但它有适用边界：

| 场景 | 适合直觉 | 适合结构化 |
|------|---------|-----------|
| 决策影响范围 | 单个模块/函数 | 跨系统/跨团队 |
| 可逆性 | 容易回退 | 难以回退或代价极高 |
| 时间压力 | 需要立即决定 | 有 1 天以上的思考时间 |
| 利益相关方 | 只影响自己 | 影响多人/多团队 |
| 信息完整度 | 信息充分、模式清晰 | 信息不完整、有不确定性 |
| 先例 | 做过很多次 | 第一次遇到或情况特殊 |

**核心原则**：[[Jeff Bezos]] 的 Type 1 / Type 2 决策分类——

- **Type 1（不可逆决策）**：像走过一扇单向门，一旦做了就很难回头。必须慎重、结构化、慢决策。
- **Type 2（可逆决策）**：像走过一扇双向门，不满意可以退回来。应该快速决策、快速验证。

大多数工程师的错误是：**把 Type 2 决策当 Type 1 来做**（过度分析、决策瘫痪），或者**把 Type 1 决策当 Type 2 来做**（拍脑袋、事后后悔）。

## 框架一：ADR（Architecture Decision Records）

### 什么是 ADR？

ADR 是一种轻量级的决策文档格式，由 Michael Nygard 在 2011 年提出，[[Martin Fowler]] 在其网站上大力推广。核心思想：**每个重要的架构决策都应该被记录下来，包括上下文、决策本身和后果**。

### ADR 模板

```markdown
# ADR-001: 选择 PostgreSQL 作为主数据库

## 状态
已接受（2026-07-19）

## 上下文
- 我们需要一个关系型数据库来存储用户数据和订单数据
- 预期 1 年内数据量达到 5000 万行
- 团队有 3 人熟悉 PostgreSQL，1 人熟悉 MySQL
- 需要支持 JSON 字段（部分非结构化数据）
- 部署环境为 AWS

## 决策
选择 PostgreSQL 15 作为主数据库，使用 RDS 托管服务。

## 考虑的替代方案
- MySQL 8.0：团队熟悉度较低，JSON 支持不如 PG
- MongoDB：数据有强关系性，不适合文档型
- TiDB：当前规模不需要分布式，增加运维复杂度

## 后果
- 正面：团队熟悉度高、JSON 支持好、AWS RDS 生态成熟
- 负面：单点扩展有上限，未来可能需要分库分表
- 风险：如果数据增长超预期，需要在 18 个月内评估分片方案

## 回顾时间
2027-01 回顾此决策是否仍然合适
```

### ADR 的核心价值

1. **防止重复讨论**：三个月后新人问「为什么用 PG 不用 MySQL」，指向 ADR 即可
2. **记录 Why 而不只是 What**：代码告诉你「是什么」，ADR 告诉你「为什么」
3. **支持未来决策**：当条件变化时，可以回顾当初的假设是否还成立
4. **降低 bus factor**：决策知识不再只存在于某个人的脑子里

### ADR 实践建议

- 存放在代码仓库中（如 `docs/adr/`），和代码一起版本管理
- 编号递增，永不删除（可以标记为「已废弃」并指向新 ADR）
- 保持简短：每个 ADR 不超过一页
- 不是所有决策都需要 ADR——只记录影响架构方向的决策

## 框架二：加权评分矩阵

### 适用场景

当有多个候选方案，且评估维度不止一个时，加权评分矩阵能把模糊的「感觉」变成可比较的结构化分析。

### 操作步骤

**第一步：列出候选方案**（通常 2-4 个）

**第二步：确定评估维度**（通常 4-7 个）

**第三步：为每个维度分配权重**（总和为 100%）

**第四步：为每个方案在每个维度上打分**（1-5 分）

**第五步：计算加权总分，讨论结果**

### 实例：选择消息队列

| 维度 | 权重 | Kafka | RabbitMQ | RocketMQ |
|------|------|-------|----------|----------|
| 吞吐量 | 30% | 5 | 3 | 4 |
| 延迟 | 15% | 3 | 5 | 4 |
| 运维复杂度 | 20% | 2 | 4 | 3 |
| 团队熟悉度 | 15% | 3 | 4 | 2 |
| 生态和文档 | 10% | 5 | 4 | 3 |
| 社区活跃度 | 10% | 5 | 4 | 3 |
| **加权总分** | 100% | **3.85** | **3.90** | **3.35** |

### 使用注意事项

- **权重分配本身就是最重要的决策**——它反映了你的价值判断
- 打分时尽量基于数据（benchmark、文档），而不是纯感觉
- 总分接近时（差距 < 0.3），说明两个方案差不多，此时应该看「最短板」而不是「平均分」
- 矩阵是辅助工具，不是最终裁决——如果结果和你的直觉严重冲突，值得深入分析为什么

## 框架三：Pre-Mortem（事前验尸）

### 核心理念

[[逆向思维：先想怎么失败，再想怎么成功]] 在技术决策中的具体应用。

传统做法是做完决策后想「怎么让它成功」。Pre-Mortem 反过来：**假设决策已经执行了一年，但彻底失败了——为什么会失败？**

### 操作步骤

1. **召集团队**（所有相关方）
2. **宣布假设**：「现在是 2027 年 7 月，我们选择的微服务架构彻底失败了。系统频繁超时、团队疲于奔命、业务方极度不满。」
3. **每人独立写下**：「你认为导致失败的原因是什么？」（5-10 分钟）
4. **轮流分享**，不做评判，只收集
5. **归类整理**：把相似的原因归为一组
6. **针对高概率风险制定预防措施**

### 实例：微服务拆分的 Pre-Mortem

假设一年后微服务拆分失败，可能的原因：

| 失败原因 | 概率 | 预防措施 |
|---------|------|---------|
| 服务间调用链过长，延迟不可控 | 高 | 限制调用深度 ≤ 3 层，引入链路追踪 |
| 团队没有分布式系统经验 | 高 | 拆分前做 2 周培训 + 试点一个服务 |
| 数据一致性无法保证 | 中 | 先做 Saga 模式 POC |
| 运维复杂度爆炸 | 中 | 先建好 CI/CD 和监控再拆 |
| 拆分粒度不对，频繁跨服务改需求 | 中 | 用 DDD 做领域建模再拆 |

### Pre-Mortem 的价值

- 打破「群体思维」：在决策前给每个人表达担忧的安全空间
- 发现盲区：不同角色（开发、运维、产品）会看到不同的风险
- 变被动为主动：不是等问题出现再救火，而是提前预防
- 降低过度乐观：人类天然倾向于高估成功概率，Pre-Mortem 强制你面对失败可能

## 框架四：可逆性分析（Bezos Type 1/Type 2）

### 决策分类矩阵

| | 高影响 | 低影响 |
|---|--------|--------|
| **不可逆** | Type 1：慎重决策 | 少见（通常不值得花太多时间） |
| **可逆** | Type 2：快速决策 + 验证 | 直接做，不用分析 |

### Type 1 决策的处理方式

- 投入充分时间（天/周级别）
- 收集多方信息
- 使用 ADR + 加权矩阵 + Pre-Mortem
- 需要多人参与决策（不是一个人拍板）
- 设定「回顾点」：什么条件下需要重新评估？

**典型 Type 1 决策**：
- 选择主数据库/编程语言/核心框架
- 单体拆微服务
- 自建 vs 购买核心系统
- 数据迁移方案
- 技术栈全面升级

### Type 2 决策的处理方式

- 快速决定（分钟/小时级别）
- 一个人就能拍板
- 不需要写 ADR
- 设定验证标准：怎么知道这个决策是对的？
- 如果验证失败，快速回退

**典型 Type 2 决策**：
- 用哪个日志库
- API 的 URL 命名风格
- 某个函数的实现方式
- 用 Redis 还是 Memcached 做缓存（大多数场景）

### [[Jeff Bezos]] 的决策哲学

Bezos 在 Amazon 内部反复强调：

> 「大多数决策是 Type 2 的，可以用快速流程。如果你用 Type 1 的流程来做 Type 2 决策，你会慢到无法忍受。如果你用 Type 2 的流程来做 Type 1 决策，你会犯下无法挽回的错误。」

> 「当你只有 70% 的信息时就应该做决策。如果等到 90%，你大概率已经晚了。」

## 框架五：[[第一性原理：从基本事实重新推导]]

### 什么时候用第一性原理？

当你面对一个「大家都这么做」的决策时，先停下来问：**这个做法的底层假设还成立吗？**

### 操作步骤

1. **识别假设**：「我们选择微服务，是因为...」
2. **追问到底**：「为什么需要这样？这个约束是真实的还是历史的？」
3. **回到基本事实**：「我们的实际 QPS 是多少？团队有多少人？业务复杂度如何？」
4. **从基本事实重新推导**：「基于这些事实，最合适的方案是什么？」

### 实例：[[Elon Musk]] 的火箭成本分析

Musk 创业时发现火箭极其昂贵。行业共识是「火箭就是贵」。他用第一性原理分析：

- 火箭的原材料成本（铝合金、碳纤维、钛）只占售价的 2%
- 剩下的 98% 是制造流程、供应链、历史惯例的成本
- 结论：如果能重新设计制造流程，成本可以降低一个数量级

**技术决策中的类比**：
- 「我们必须用微服务」→ 为什么？→ 「因为 Netflix 这么做」→ 但 Netflix 有 500 个工程师，我们只有 8 个
- 「我们必须用 Kubernetes」→ 为什么？→ 「因为大家都在用」→ 但我们的服务只有 3 个，Docker Compose 就够了

## 决策疲劳管理

### 问题：决策太多，质量下降

研究表明，人每天能做出的高质量决策是有限的。当决策疲劳累积时，人会倾向于：
- 选择默认选项（不做改变）
- 选择最省力的选项（而不是最好的）
- 推迟决策（导致项目延误）

### 应对策略

**1. 减少不必要的决策**

- 建立团队约定：代码风格、命名规范、项目结构——这些不需要每次讨论
- 使用 [[Martin Fowler]] 推荐的「约定优于配置」原则
- 把重复性决策变成 checklist 或自动化

**2. 把重要决策放在最佳时间**

- 大多数人上午的决策质量最高
- 不要在下午 5 点做架构决策
- 给重要决策留出「无干扰时间块」

**3. 设定决策截止日**

- 「这个决策必须在周五前做出」
- 避免无限期拖延（分析瘫痪）
- 70% 的信息 + 明确的截止日 > 100% 的信息 + 无限期等待

**4. 委托和分级**

- 不是所有决策都需要你来做
- Type 2 决策委托给最了解情况的人
- 只保留 Type 1 决策和跨团队决策给自己

## 共识 vs 权威：决策模式选择

### 不同决策模式对比

| 模式 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| 权威决策（一人拍板） | 紧急、Type 2、信息集中在一人 | 快速、清晰 | 可能遗漏信息、团队不认同 |
| 共识决策（全员同意） | Type 1、影响全团队、需要全员执行 | 高认同度、多角度 | 慢、可能妥协出平庸方案 |
| 咨询决策（一人拍板 + 征求输入） | 大多数架构决策 | 平衡速度和质量 | 需要明确谁是最终决策者 |
| 投票决策（多数决定） | 偏好类选择（工具、风格） | 民主、快速 | 少数派可能不认同 |

### 推荐模式：「Disagree and Commit」

[[Jeff Bezos]] 和 [[Werner Vogels]] 在 Amazon 推行的原则：

1. 充分讨论，每个人表达观点
2. 最终由决策者（通常是 tech lead 或架构师）拍板
3. 即使你不同意，一旦决策做出，全力执行
4. 如果后续事实证明决策错误，可以 revisit——但不是在执行阶段继续争论

**关键**：这不是独裁。决策者有义务认真听取所有输入，并解释为什么做了这个选择。

## 经典决策案例分析

### 案例一：选择数据库

**背景**：创业项目，10 人团队，需要选择主数据库

**Type 判定**：Type 1（换数据库代价极高）

**决策过程**：
1. 第一性原理：我们的数据模型是什么？关系型还是文档型？→ 强关系，选关系型
2. 加权矩阵：PostgreSQL vs MySQL vs MongoDB
3. Pre-Mortem：如果选错了，最可能因为什么？→ 团队不熟悉、扩展性不够
4. 最终决策：PostgreSQL（团队熟悉 + JSON 支持 + 扩展性好）
5. 写 ADR 记录

### 案例二：Build vs Buy

**背景**：需要用户认证系统，自建还是用 Auth0/Clerk？

**Type 判定**：中等——可以迁移，但迁移成本不低

**决策过程**：
1. 第一性原理：认证是我们的核心竞争力吗？→ 不是
2. 成本分析：自建需要 2 人 × 3 月 + 持续维护；购买是 $500/月
3. Pre-Mortem：如果买了，最可能后悔的原因？→ 供应商锁定、定制化不够
4. 最终决策：先买（快速上线），但抽象认证接口（降低未来迁移成本）
5. 设定回顾点：用户量超过 10 万时重新评估

### 案例三：单体 vs 微服务

**背景**：业务增长，单体应用开始变慢，团队从 5 人扩展到 20 人

**Type 判定**：Type 1（拆分后很难合回来）

**决策过程**：
1. 第一性原理：我们的痛点到底是什么？→ 部署耦合（改一个模块要全量发布）还是性能瓶颈？
2. 发现：主要是部署耦合，不是性能问题
3. 替代方案：不一定要微服务，可以先做模块化单体（Modular Monolith）
4. Pre-Mortem：如果拆微服务，最可能失败的原因？→ 团队没有分布式经验
5. 最终决策：先做模块化单体（解决部署耦合），观察 6 个月，再决定是否需要微服务
6. 写 ADR，设定 6 个月回顾点

## 文档化决策：为未来的自己写信

### 为什么必须文档化？

[[Werner Vogels]]（Amazon CTO）说过：

> 「六个月后你会忘记自己为什么做了这个决策。如果没有记录，你会花三倍时间来重新分析，或者更糟——基于错误的记忆做出错误的后续决策。」

### 文档化的最小集

对于每个 Type 1 决策，至少记录：

1. **上下文**：当时面临什么问题？有什么约束？
2. **决策**：最终选了什么？
3. **原因**：为什么选这个？关键 trade-off 是什么？
4. **替代方案**：考虑过什么？为什么没选？
5. **回顾条件**：什么情况下需要重新评估？

### 存放位置

- ADR 放在代码仓库的 `docs/adr/` 目录
- 重大技术选型放在团队 Wiki
- 和代码一起 review、一起版本管理
- 新人 onboarding 时必读

## 反模式：技术决策中的常见陷阱

### 1. 简历驱动开发（Resume-Driven Development）

- **表现**：选择技术不是因为适合项目，而是因为想写在简历上
- **危害**：引入不必要的复杂度，团队学习成本高
- **解药**：决策时问「如果这个技术不能写在简历上，我还会选它吗？」

### 2. 锤子综合征（Law of the Instrument）

- **表现**：「我只会 Kubernetes，所以所有项目都用 Kubernetes」
- **危害**：用错误的工具解决问题，增加不必要的复杂度
- **解药**：先定义问题和约束，再选工具——而不是反过来

### 3. 分析瘫痪（Analysis Paralysis）

- **表现**：花了 3 周调研 5 个方案，写了 20 页对比文档，还是做不出决定
- **危害**：项目延期，团队士气下降
- **解药**：设定决策截止日；记住「70% 信息就够做决策」；Type 2 决策不要过度分析

### 4. 从众决策（Bandwagon Effect）

- **表现**：「Netflix/Google/字节都这么做，所以我们也这么做」
- **危害**：大公司的方案是为大公司的规模和约束设计的，不一定适合你
- **解药**：用 [[第一性原理：从基本事实重新推导]]——你的约束和他们一样吗？

### 5. 沉没成本谬误

- **表现**：「我们已经在这个技术上投入了 6 个月，不能换」
- **危害**：在错误的路上越走越远
- **解药**：决策时只看未来成本和收益，不看过去投入了多少。问自己：「如果今天从零开始，我还会选这个吗？」

### 6. 决策后不回顾

- **表现**：做完决策就忘了，从不检查决策是否仍然合适
- **危害**：条件已经变了，但还在执行过时的决策
- **解药**：每个 Type 1 决策设定回顾日期，到期评估假设是否还成立

## 立即行动

**本周可以做**（选 1-2 项执行）：

- [ ] 回顾你最近做的一个技术决策，用 ADR 格式把它记录下来（即使已经做完了）
- [ ] 列出你当前项目中「正在拖延」的技术决策，判断它是 Type 1 还是 Type 2，给 Type 2 设定 48 小时截止日
- [ ] 对你正在做的一个技术选型，花 30 分钟做一次 Pre-Mortem：如果这个选择一年后失败了，最可能因为什么？
- [ ] 在代码仓库中创建 `docs/adr/` 目录，写下第一个 ADR

**本季度可以做**：

- [ ] 建立团队的 ADR 实践：每个架构决策必须有对应的 ADR
- [ ] 对下一个 Type 1 决策，完整走一遍结构化流程（加权矩阵 + Pre-Mortem + ADR）
- [ ] 回顾 6 个月前做的 2-3 个技术决策：假设还成立吗？需要调整吗？
- [ ] 在团队中做一次「决策复盘」分享：哪些决策做对了？哪些做错了？为什么？
- [ ] 建立团队的「技术决策原则」文档：我们做决策时遵循什么价值观？（如「简单优先」「可逆优先」）

**长期目标**：

- [ ] 积累 20+ 个 ADR，形成项目的「决策历史」
- [ ] 建立个人决策直觉：通过大量结构化决策的练习，让好的决策模式内化为直觉
- [ ] 能够根据场景灵活切换决策模式：快速直觉 / 结构化分析 / 团队共识
- [ ] 帮助团队建立健康的决策文化：允许犯错、鼓励质疑、重视回顾
