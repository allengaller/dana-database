# 如何评估一家技术公司

无论是求职选择 offer、考虑加入早期创业公司、还是作为投资者做技术尽调，你都需要一套系统化的框架来评估一家技术公司。大多数人的评估方式极其粗糙——看融资轮次、看产品知名度、看薪资数字——然后凭直觉做决定。

本文提供一套多维度的评估框架，帮助你穿透营销话术和表面光环，看到一家技术公司的真实技术能力、工程文化和长期潜力。

---

## 为什么需要这个方法论

### 信息不对称的困境

评估技术公司面临的核心挑战是**信息不对称**：

- **求职场景**：公司精心包装了招聘页面、面试流程、offer 谈判。你看到的「工程文化」可能是 HR 写的剧本，而非工程师的日常。
- **投资场景**：创始人展示的是最好的数据、最乐观的预测。技术架构的「demo 版本」和「生产版本」可能天差地别。
- **合作场景**：技术合作伙伴展示的是成功案例，隐藏的是失败教训和技术债务。

### 常见评估误区

| 误区 | 为什么是误区 | 正确做法 |
|------|------------|---------|
| 「融资多 = 技术强」 | 融资反映的是融资能力和市场热度，不是技术实力 | 看技术壁垒和工程效率 |
| 「产品有名 = 工程文化好」 | 产品成功可能靠市场/运营，工程团队可能在受苦 | 直接与工程师交流 |
| 「薪资高 = 值得去」 | 高薪可能补偿的是加班、技术债、无成长 | 综合评估成长性和工作质量 |
| 「技术栈新 = 技术强」 | 用最新框架可能是追新，也可能是没有历史包袱 | 看技术选型的决策过程 |
| 「GitHub star 多 = 开源做得好」 | Star 数反映营销，不反映代码质量和维护可持续性 | 看 issue 响应、PR 质量、社区治理 |

### 评估的 stakes

- **求职**：一份工作占据你每天 8-12 小时、持续 2-5 年。选错公司的代价是巨大的——技术成长停滞、心理健康受损、职业路径偏移。
- **投资**：技术判断失误可能导致数百万甚至数亿的投资打水漂。
- **合作**：与一个技术能力不足的公司深度合作，可能拖垮你自己的产品和团队。

**核心原则**：评估技术公司不是看它「说什么」，而是看它「做什么」和「怎么做」。

## 核心框架

### 维度一：技术护城河（Technical Moat）

技术护城河回答的核心问题是：**这家公司的技术优势是否可持续？竞争对手复制它需要多长时间？**

#### 评估清单

| 指标 | 强信号 | 弱信号 |
|------|--------|--------|
| 核心算法/模型 | 自研核心算法，有论文/专利支撑 | 调用第三方 API，无自研成分 |
| 数据壁垒 | 拥有独特的、难以获取的数据集 | 使用公开数据集，无数据优势 |
| 系统复杂度 | 系统经过多年迭代，有大量隐性知识 | 系统简单，任何团队都能重建 |
| 切换成本 | 用户迁移代价高（数据锁定、工作流集成） | 用户可以轻松切换到竞品 |
| 技术人才密度 | 核心领域有 3+ 名顶级专家 | 依赖 1 个「技术大牛」，无梯队 |
| 开源/标准贡献 | 主导或深度参与行业标准/开源项目 | 无外部技术影响力 |

#### 深度问题（面试/尽调时问）

- 「你们的核心技术壁垒是什么？如果竞争对手有 10 倍资金，他们需要多久才能复制？」
- 「你们的技术选型中，哪些是'有意为之的差异化'，哪些是'行业标准做法'？」
- 「过去两年，你们在核心技术上做了什么竞争对手没做的创新？」
- 「如果你们的首席架构师明天离职，系统还能正常演进吗？」

#### 护城河的层次

```
第一层（最弱）：先发优势 —— 只是比别人早做了
第二层：规模效应 —— 用户越多，系统越好（网络效应、数据飞轮）
第三层：技术深度 —— 核心算法/系统有真正的技术含量
第四层（最强）：生态系统 —— 围绕技术建立了开发者/合作伙伴生态
```

### 维度二：工程文化（Engineering Culture）

工程文化回答的核心问题是：**在这家公司做工程师，日常体验是什么？技术决策是如何做出的？**

#### 评估清单

| 指标 | 强信号 | 弱信号 |
|------|--------|--------|
| 代码质量 | 有 code review 文化、CI/CD 完善、测试覆盖合理 | 「先上线再说」、无 review、手动部署 |
| 技术债务管理 | 有明确的技术债务追踪和偿还计划 | 「技术债是什么？我们没时间管这个」 |
| 决策过程 | 有 RFC/设计文档流程，决策透明 | 老板拍脑袋、朝令夕改 |
| 学习成长 | 有 tech talk、读书时间、会议预算 | 「学习是你自己的事，别占用工作时间」 |
| 工程师话语权 | 技术选型由工程师决定，PM 不干预实现 | 「PM 说了算，你只管写代码」 |
| 事故处理 | Blameless postmortem，关注系统改进 | 出事找人背锅，惩罚性文化 |
| 工作节奏 | 可持续的 pace，尊重个人时间 | 996 是常态，「奋斗者文化」 |

#### 深度问题

- 「你们最近一次生产事故是怎么处理的？能描述一下 postmortem 过程吗？」
- 「工程师有多少时间用于技术改进（vs 纯功能开发）？」
- 「一个新功能从 idea 到上线，中间经过哪些技术评审环节？」
- 「你们怎么处理'PM 要的功能'和'工程师想做的重构'之间的冲突？」
- 「最近一年，有多少工程师主动离职？主要原因是什么？」（问 HR 或看 LinkedIn）

#### 观察信号（面试/参观时）

- **代码仓库**：能否看到 CI 状态？PR 是否有 review？commit message 是否有意义？
- **内部文档**：是否有设计文档、runbook、onboarding 文档？还是全靠口口相传？
- **工程师状态**：面试你的工程师看起来是兴奋的还是疲惫的？他们谈论技术时眼睛有光吗？
- **工具链**：用什么工具管理代码、部署、监控？是现代化的还是 10 年前的？

### 维度三：增长轨迹（Growth Trajectory）

增长轨迹回答的核心问题是：**这家公司是在上升期还是停滞期？未来 3-5 年会怎样？**

#### 评估清单

| 指标 | 强信号 | 弱信号 |
|------|--------|--------|
| 收入增长 | YoY 增长 > 50%（早期）或 > 20%（成熟期） | 增长停滞或依赖融资续命 |
| 用户增长 | 有机增长为主，NPS > 50 | 依赖烧钱获客，留存率低 |
| 市场空间 | TAM 大且未被充分开发 | 市场已饱和或正在萎缩 |
| 产品演进 | 定期发布重大功能，路线图清晰 | 产品停滞，只做维护 |
| 技术投资 | 持续投入基础设施和新方向 | 技术投入被压缩，「能跑就行」 |
| 人才吸引 | 能吸引到顶级人才加入 | 核心人才持续流失 |

#### 深度问题

- 「过去 12 个月，你们最重要的 3 个技术里程碑是什么？」
- 「未来 2 年，技术团队最大的挑战是什么？」
- 「你们的技术路线图是如何制定的？工程师参与多少？」
- 「公司的 runway 还有多长？」（早期公司必问）
- 「你们最大的技术风险是什么？如果 X 技术方向走错了怎么办？」

#### 增长阶段的匹配

| 公司阶段 | 适合什么人 | 风险 | 回报 |
|---------|-----------|------|------|
| 种子/天使 | 高风险偏好、想从 0 到 1 | 极高（90% 失败） | 极高（股权） |
| A-B 轮 | 想快速成长、能接受混乱 | 高（50% 失败） | 高（股权 + 成长） |
| C-D 轮 | 想参与规模化、有一定稳定性 | 中（20% 失败） | 中（股权 + 薪资） |
| 上市/成熟 | 想深耕专业领域、稳定 | 低 | 低-中（RSU + 薪资） |

### 维度四：领导力与治理（Leadership & Governance）

领导力回答的核心问题是：**做决策的人是否值得信赖？他们是否有能力带领公司走对方向？**

#### 评估清单

| 指标 | 强信号 | 弱信号 |
|------|--------|--------|
| 技术领导力 | CTO/VP Eng 有深厚的技术背景和判断力 | 技术领导是纯管理者，不懂技术 |
| 决策质量 | 过去的重大技术决策被证明是正确的 | 频繁推翻之前的决策、技术方向摇摆 |
| 透明度 | 定期全员分享公司状态、挑战 | 信息高度不透明，「你不需要知道」 |
| 对技术的尊重 | 技术被视为核心竞争力而非成本中心 | 「技术就是实现 PM 需求的工具」 |
| 人才发展 | 有清晰的工程师成长路径（IC track） | 唯一的晋升方式是转管理 |
| 创始人特质 | 学习能力强、诚实、有长期思维 | 过度营销、短期主义、不承认错误 |

#### 深度问题

- 「CTO/技术 VP 的技术背景是什么？他们现在还写代码吗？」
- 「过去两年，公司做过最艰难的技术决策是什么？结果如何？」
- 「工程师的职业发展路径是什么？IC（个人贡献者）最高能到什么级别？」
- 「当技术判断和商业判断冲突时，通常怎么解决？」
- 「创始人/CEO 对技术的理解程度如何？他们能区分'难'和'不可能'吗？」

### 维度五：团队与协作（Team & Collaboration）

#### 评估清单

| 指标 | 强信号 | 弱信号 |
|------|--------|--------|
| 团队稳定性 | 核心成员 3+ 年，低离职率 | 高频换人，「铁打的营盘流水的兵」 |
| 知识分布 | 关键知识不依赖单一个人 | Bus factor = 1（一个人走了系统就瘫） |
| 跨团队协作 | 有清晰的接口和协作流程 | 跨团队合作靠「找人」、「刷脸」 |
| 新人融入 | 有结构化的 onboarding，2 周内能提交代码 | 「自己看代码、自己摸索」，3 个月还没上手 |
| 多样性 | 团队背景多元，有不同视角 | 同质化严重，群体思维 |

## 实战案例

### 案例一：求职评估——两个 offer 的对比

**背景**：一位 5 年经验的后端工程师，同时收到两个 offer：

| 维度 | 公司 A（大厂） | 公司 B（B 轮创业公司） |
|------|--------------|---------------------|
| 技术护城河 | 强——自研分布式系统，10 年积累 | 中——核心算法自研，但系统较简单 |
| 工程文化 | 成熟——完善的 CI/CD、review、oncall | 粗糙——快速迭代，技术债多 |
| 增长轨迹 | 稳定——年增长 10-15% | 快速——年增长 80%，但 runway 18 个月 |
| 领导力 | 职业经理人，稳定但缺乏激情 | 创始人是技术出身，有远见但经验不足 |
| 个人成长 | 深耕一个领域，但视野受限 | 全栈参与，成长快但可能不系统 |
| 薪资 | 高 30%（含 RSU） | 低 30% + 期权（可能归零） |

**分析**：没有「正确答案」，取决于个人优先级：
- 如果优先「系统性学习工程实践」→ 公司 A
- 如果优先「快速成长和多元体验」→ 公司 B
- 如果优先「财务安全」→ 公司 A
- 如果优先「上行空间（期权）」→ 公司 B

**关键洞见**：评估框架不帮你做决定，它帮你**看清 trade-off**。大多数人后悔不是因为选错了，而是因为**没有看清自己在 trade 什么**。

### 案例二：投资尽调——AI 创业公司的技术评估

**背景**：一位天使投资人考虑投资一家「AI 客服」创业公司。

**表面信号**：
- 产品 demo 效果很好
- 创始人是前大厂 AI 研究员
- 已有 10 个付费客户
- 种子轮融资 $2M

**深度评估发现**：
- 技术护城河弱：核心是调用 GPT-4 API + 简单的 prompt engineering，无自研模型
- 数据壁垒弱：客户数据归客户所有，公司没有积累独特数据集
- 工程文化差：没有测试、没有 CI、代码质量低（「先跑起来再说」）
- 团队风险：核心开发只有 2 人，bus factor = 1
- 竞争壁垒：任何有 API 访问权限的团队都能在 2 周内复制

**结论**：技术护城河几乎不存在。如果 OpenAI 或大厂推出类似功能（概率极高），公司没有任何防御能力。不投。

**6 个月后验证**：该公司确实因为大厂推出竞品而失去大部分客户，最终关闭。

### 案例三：技术合作评估——选择云服务提供商

**背景**：一家中型 SaaS 公司评估是否将核心系统迁移到某新兴云平台。

**评估维度应用**：
- 技术护城河：该平台有独特的 serverless 架构，性能确实优于竞品 ✓
- 工程文化：开源社区活跃，issue 响应快，文档质量高 ✓
- 增长轨迹：用户增长快，但收入模式不清晰 △
- 领导力：创始人技术背景强，但公司只有 50 人 △
- 风险：如果公司倒闭或被收购，迁移成本极高 ✗

**结论**：技术优秀但公司可持续性存疑。决策：非核心系统可以试用，核心系统不迁移，保持多云架构降低锁定风险。

## 常见错误

### 错误一：光环效应

**表现**：因为公司有一个优点（例如「融资多」或「创始人有名」），就假设所有维度都好。

**修正**：每个维度独立评估。融资多不代表工程文化好，创始人有名不代表技术护城河强。

### 错误二：只看当下不看趋势

**表现**：「这家公司现在技术很强」——但没考虑 3 年后是否还能保持。

**修正**：评估趋势比评估现状更重要。一家现在 70 分但快速进步的公司，可能比一家现在 90 分但停滞的公司更值得加入。

### 错误三：忽视「人」的因素

**表现**：只评估技术架构和产品，不评估团队和领导。

**修正**：技术是人做的。一个优秀的团队可以在烂架构上重建，一个烂团队可以在好架构上搞砸。优先评估人。

### 错误四：被「技术栈」迷惑

**表现**：「他们用 Rust + Kubernetes + 最新的 AI 框架，一定很强！」

**修正**：技术栈是选择，不是能力。一个用 Java 8 + 单体架构但工程实践极好的团队，远胜于一个用最新技术栈但代码质量一塌糊涂的团队。

### 错误五：忽视自己的需求

**表现**：客观评估了公司所有维度，但没有评估「这家公司是否适合我」。

**修正**：评估是双向的。一家「客观上很好」的公司可能不适合你——你可能需要更多自主权、更慢的节奏、或不同的技术方向。参见 [[能力圈与边界意识]]。

## 工具与模板

### 公司评估打分卡

| 维度 | 权重 | 评分(1-5) | 加权分 | 备注 |
|------|------|-----------|--------|------|
| 技术护城河 | 25% | | | |
| 工程文化 | 25% | | | |
| 增长轨迹 | 20% | | | |
| 领导力 | 15% | | | |
| 团队与协作 | 15% | | | |
| **总分** | 100% | | | |

**评分标准**：
- 5 = 业界顶级，明显优于大多数公司
- 4 = 优秀，高于平均
- 3 = 平均，没有明显优点也没有明显缺点
- 2 = 低于平均，有明确的问题
- 1 = 严重问题，红旗信号

### 面试/尽调问题清单（按角色）

**问工程师**：
1. 描述你最近解决的最有挑战性的技术问题
2. 你们的 code review 流程是怎样的？
3. 最近一次生产事故是什么？怎么处理的？
4. 你有多少时间用于技术改进 vs 功能开发？
5. 如果你能改变公司技术实践的一件事，你会改什么？

**问技术领导**：
1. 你们最大的技术风险是什么？
2. 过去两年最艰难的技术决策是什么？
3. 你们怎么平衡短期交付和长期技术投资？
4. 工程师的成长路径是什么？
5. 你们怎么吸引和留住顶级技术人才？

**问产品/业务领导**：
1. 技术在公司的战略定位是什么？成本中心还是竞争力？
2. 当技术说「这需要 3 个月重构」时，通常怎么回应？
3. 你们的技术路线图是如何制定的？
4. 公司对技术失败的容忍度如何？

### 红旗信号速查表

以下任何一条出现，都需要高度警惕：

- 「我们不需要 code review，大家都很忙」
- 「测试太慢了，我们直接上线」
- 「CTO 已经 3 年没写过代码了」
- 「我们的架构师走了，现在没人懂核心系统」
