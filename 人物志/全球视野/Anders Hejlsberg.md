# Anders Hejlsberg：从 Turbo Pascal 到 TypeScript，四十年语言设计的持续卓越

> **"编程语言的设计不是关于添加特性，而是关于移除障碍。你要移除的是程序员与他的意图之间的所有摩擦。"**
> — Anders Hejlsberg，Microsoft Build 演讲，2012

Anders Hejlsberg 是编程语言设计史上最罕见的存在——他不是只创造了一门伟大语言，而是在四十年的职业生涯中，**连续创造了四门影响深远的语言/工具**：

- 1983 年，他在丹麦独自编写了 **Turbo Pascal** 编译器，以极快的编译速度和极低的价格颠覆了整个 Pascal 市场
- 1995 年，他在 Borland 主导设计了 **Delphi**（Object Pascal），将可视化编程与强类型系统结合，定义了 Windows 快速应用开发的时代
- 2000 年，他加入 Microsoft 后主导设计了 **C#**，这门语言如今是 .NET 生态的核心，服务数百万企业开发者
- 2012 年，他在 52 岁时再次出发，设计了 **TypeScript**，为混乱的 JavaScript 世界带来了类型安全，如今已成为前端工程的事实标准

一个人，四门语言，跨越四十年，每一门都在其时代产生了巨大影响。这在技术史上几乎没有先例。

我们研究他，不是因为他"天赋异禀"（虽然确实是），而是因为他展示了**一种可学习的方法论**：如何在不同时代、不同平台、不同约束下，持续做出正确的语言设计决策。他的每一次成功都不是偶然的——背后是对程序员真实痛点的深刻洞察、对"渐进式改进"的坚持、以及对"不破坏用户代码"的近乎偏执的承诺。

---

## 为什么值得学

对 3-7 年技术人而言，Anders Hejlsberg 的独特价值在于三个层面：

**第一，他证明了"语言设计"是一种可以持续精进的手艺。** 大多数程序员终其职业生涯只使用语言，少数人设计 DSL 或内部框架，而 Anders 把"设计语言"本身当作一门手艺来打磨。从 Turbo Pascal 到 TypeScript，他的设计哲学在不断演化：从追求编译速度，到追求开发体验，到追求类型安全与渐进式采用的平衡。这种"同一领域内的持续进化"比"不断换赛道"更有学习价值。

**第二，他展示了"渐进式改进"如何战胜"推倒重来"。** C# 没有试图取代 C++，TypeScript 没有试图取代 JavaScript。Anders 的每一次设计都是在现有生态上做增量改进——保留用户已有的投资和习惯，同时引入关键的改进。这种策略让他的语言能够被大规模采用，而不是停留在学术圈或小众社区。

**第三，他的职业选择本身就是教科书。** 从丹麦小公司到 Borland 的辉煌，再到 Microsoft 的长期深耕，Anders 展示了技术人如何在"创造力"和"平台资源"之间找到平衡。他 1996 年从 Borland 跳槽到 Microsoft 的故事，是技术史上最经典的"人才争夺战"案例之一——Microsoft 为此支付了数千万美元的补偿金。

## 关键转折与心法

### 转折一：在丹麦独自编写 Turbo Pascal 编译器（1981-1983）——一个人对抗一个行业

1980 年代初，Pascal 编译器市场被少数几家公司垄断，价格高达数百甚至上千美元，编译速度极慢。Anders 当时还是丹麦技术大学的学生，他决定自己写一个 Pascal 编译器。

他做了一件在当时看来不可能的事：**用汇编语言手写了一个完整的 Pascal 编译器，使其能在 64KB 内存的 CP/M 机器上运行，编译速度达到每秒数千行代码。** 1983 年，Borland 的创始人 Philippe Kahn 看到了这个编译器，立即与 Anders 合作，以 49.95 美元的价格发布了 Turbo Pascal 1.0。

这个价格只有竞争对手的十分之一，编译速度却快了一个数量级。Turbo Pascal 迅速成为 PC 编程教育的标准工具，影响了整整一代程序员。

**心法提炼**：**当你发现一个市场被低效的 incumbent 占据时，不要试图在同一个维度上竞争。找到被忽视的维度（速度、价格、易用性），在那个维度上做到极致。** Anders 没有在"功能完整性"上与大型编译器竞争，而是在"编译速度"和"价格"上实现了数量级的突破。

---

### 转折二：从 Turbo Pascal 到 Delphi——从工具到平台的跃迁（1989-1995）

Turbo Pascal 成功后，Anders 面临一个选择：继续改进 Pascal 编译器，还是做更大的事？他选择了后者。

1990 年代初，Microsoft 的 Visual Basic 正在快速占领 Windows 应用开发市场。VB 的优势是可视化拖拽编程，劣势是弱类型、性能差、不适合大型项目。Anders 看到了机会：**能不能把 VB 的可视化开发体验，与 Pascal 的强类型系统和编译性能结合起来？**

这就是 Delphi 的起源。1995 年发布的 Delphi 1.0 引入了：
- 可视化组件库（VCL）：拖拽式 UI 开发
- 强类型面向对象系统：编译时类型检查
- 原生代码编译：性能远超 VB
- 组件属性编辑器：所见即所得

Delphi 在 1990 年代中后期成为 Windows 开发的主流选择之一，与 VB、VC++ 三足鼎立。

**心法提炼**：**不要发明全新的范式，而是把两个已验证的优势组合起来。** Delphi 没有发明可视化编程（VB 已有），也没有发明强类型 OOP（C++ 已有），但它把两者结合在一个一致的框架中，创造了 1+1>2 的效果。这种"组合式创新"比"从零发明"更容易被市场接受。

---

### 转折三：从 Borland 到 Microsoft——数千万美元的人才争夺（1996）

1996 年，Anders 在 Borland 的工作遇到了瓶颈。Borland 的管理层开始偏离技术方向，内部政治斗争加剧，Delphi 的后续版本规划受到非技术因素干扰。

Microsoft 看到了机会。Bill Gates 亲自参与了对 Anders 的招募。最终，Microsoft 以据传数千万美元的补偿金（包括股票和签约奖金）将 Anders 从 Borland 挖走。这在当时是硅谷历史上最昂贵的人才争夺之一。

Anders 后来回忆说，吸引他的不是钱，而是**规模和影响力**："在 Borland，我影响的是几十万开发者。在 Microsoft，我可以影响数百万。"

加入 Microsoft 后，Anders 被赋予了极大的自主权，领导一个全新的语言设计项目。这个项目的代号是 "Cool"（C-like Object Oriented Language），最终在 2000 年以 **C#** 的名字发布。

**心法提炼**：**选择平台时，不要只看薪资，要看"你的工作能触达多少人"。** Anders 在 Borland 已经做到了技术巅峰，但平台的天花板限制了他的影响力。有时候，换一个更大的平台不是"背叛"，而是让自己的工作产生更大价值的必要选择。

---

### 转折四：C# 的设计与演化——在 Java 的阴影下走出自己的路（2000-2010）

C# 诞生时，外界普遍认为它是"Microsoft 版的 Java"。这并非完全没有道理——C# 1.0 的语法确实与 Java 高度相似。但 Anders 从一开始就有不同的设计目标：

- **属性（Properties）**：用声明式语法替代 getter/setter 样板代码
- **事件（Events）**：一等公民的事件系统
- **委托（Delegates）**：类型安全的函数指针
- **值类型与引用类型的明确区分**：struct vs class

更重要的是 C# 后续的演化路径。Anders 主导了多个里程碑式的版本：
- C# 2.0（2005）：泛型、迭代器、匿名方法
- C# 3.0（2007）：LINQ、Lambda 表达式、类型推断——**这是编程语言历史上第一次将查询表达式作为语言一等公民**
- C# 4.0（2010）：动态类型支持
- C# 5.0（2012）：async/await——**比 JavaScript 的 async/await 早了五年**

特别是 LINQ 和 async/await，这两个特性后来被几乎所有主流语言借鉴。TypeScript 的 async/await、Python 的 async/await、Kotlin 的协程，都可以追溯到 C# 的先驱工作。

**心法提炼**：**被贴上"模仿者"标签不可怕，可怕的是停止进化。** C# 1.0 确实像 Java，但 Anders 没有停留在"兼容 Java"的层面，而是持续引入真正有价值的语言特性。到 C# 3.0 时，已经没有人再说它是"Java 克隆"了。**用持续的创新来回应质疑，而不是用辩论。**

---

### 转折五：52 岁设计 TypeScript——在 JavaScript 的混乱中建立秩序（2012-至今）

2010 年前后，JavaScript 正在经历一场身份危机。一方面，它是 Web 的唯一编程语言，使用量爆炸式增长；另一方面，它的弱类型、隐式转换、原型继承等特性让大型项目维护成为噩梦。

Anders 看到了一个关键洞察：**JavaScript 的问题不是语法问题，而是缺乏类型系统。但任何试图"替代" JavaScript 的语言都会失败，因为 Web 平台的惯性太大了。**

TypeScript 的设计策略是天才般的：
- **它是 JavaScript 的超集**：所有合法的 JS 代码都是合法的 TS 代码
- **类型是渐进式的**：你可以从 `any` 开始，逐步添加类型注解
- **类型在编译时擦除**：运行时就是纯 JavaScript，零性能开销
- **不改变 JavaScript 的语义**：只添加类型层，不修改运行时行为

2012 年 TypeScript 发布时，社区反应冷淡。很多人认为"给 JavaScript 加类型"是多此一举。但 Anders 坚持了下来。到 2017-2018 年，随着前端应用复杂度爆炸式增长，TypeScript 的采用率开始指数级增长。到 2024 年，TypeScript 已经成为前端工程的事实标准，几乎所有新项目都默认使用 TypeScript。

**心法提炼**：**解决一个巨大生态的问题，不要试图替换它，而是在它之上添加一层。** TypeScript 的成功不是因为它"比 JavaScript 好"，而是因为它"让 JavaScript 变得可管理"。这种"增量式改进"策略比"推倒重来"策略在现实中更容易成功。同时，**52 岁不是创造力的终点**——Anders 在职业生涯的第三十年创造了可能是他影响力最大的作品。

## 核心可学习点

### 1. "渐进式采用"是语言/工具设计的最高策略

从 Turbo Pascal 的"兼容标准 Pascal"到 TypeScript 的"JavaScript 超集"，Anders 的每一次设计都遵循同一个原则：**不要要求用户放弃他们已有的东西。** 新工具应该让用户可以从现有代码开始，逐步迁移，而不是一夜之间重写一切。

**行动建议**：当你设计内部工具、框架或 API 时，问自己：用户能不能在不修改现有代码的情况下开始使用？如果不能，能不能提供一个兼容层？渐进式采用的工具最终会击败"全有或全无"的工具。

### 2. 类型系统是文档、是测试、是重构工具

Anders 在 TypeScript 中证明了一个观点：**类型注解不是负担，而是最高效的文档。** 类型信息可以被编辑器用来提供自动补全、可以被编译器用来发现错误、可以被重构工具用来安全地修改代码。一份类型注解同时服务了三个目的。

**行动建议**：在你的项目中，优先为公共 API 和核心数据结构添加类型注解（无论是 TypeScript、Python 的 type hints、还是 Rust 的类型系统）。不要追求 100% 类型覆盖，但核心接口必须有类型。

### 3. 编译器速度是用户体验，不是技术指标

Turbo Pascal 的成功很大程度上归功于编译速度。Anders 始终认为：**编译速度不是"性能优化"问题，而是"开发体验"问题。** 一个需要等待 30 秒才能看到结果的编译循环，和一个 1 秒完成的编译循环，对程序员的心流状态有质的影响。

**行动建议**：关注你的项目的构建时间。如果 `npm run build` 或 `mvn compile` 需要超过 30 秒，把它当作一个 P0 级别的体验问题来对待，而不是"以后再说"的技术债。

### 4. 语言设计是"移除"而不是"添加"

Anders 多次在访谈中提到：**好的语言设计不是添加更多特性，而是移除程序员与意图之间的障碍。** C# 的属性语法移除了 getter/setter 的样板代码；TypeScript 的类型推断移除了冗余的类型注解；async/await 移除了回调地狱的认知负担。

**行动建议**：审视你写的代码或设计的 API，找出那些"用户必须写但没有任何信息量"的部分。能不能通过默认值、类型推断、或约定来消除它们？

### 5. 在正确的时机引入正确的特性

C# 的 async/await 在 2012 年引入，比 JavaScript 早了五年。TypeScript 在 2012 年引入时社区不以为然，但五年后成为标准。Anders 的能力不仅是"设计好特性"，更是"在正确的时机推出"。太早，市场还没准备好；太晚，别人已经占据了位置。

**行动建议**：当你有一个"超前"的技术想法时，不要等到"所有人都认同"才行动。先做一个最小可用版本，让早期采用者验证价值，然后等待市场成熟。TypeScript 用了五年才迎来爆发——这五年的坚持不是浪费，而是积累。

## 今天就可以开始的 3 件事

1. **用 TypeScript 重写一个你熟悉的 JavaScript 模块**
   - 选择一个你正在维护的 JS 项目中的一个小模块（200-500 行）
   - 用 `tsc --init` 初始化 TypeScript 配置，将文件改为 `.ts`
   - 体验类型系统如何帮你发现隐藏的 bug、提供自动补全
   - 注意：不要试图一步到位，从 `any` 开始，逐步收紧类型

2. **研究 C# 的 async/await 设计文档**
   - 搜索 "C# async await design document" 或 Eric Lippert 的博客系列
   - 理解为什么 C# 选择了"编译器变换"而不是"运行时支持"来实现异步
   - 思考：这个设计决策如何影响了后来 JavaScript、Python、Kotlin 的异步设计？

3. **在你的项目中实践"渐进式改进"策略**
   - 找到一个你想引入的新工具/框架/实践（比如单元测试、CI/CD、代码规范）
   - 不要试图一次性全量推广，而是设计一个"渐进式采用"路径
   - 让团队可以从一个文件、一个模块开始，逐步扩大覆盖范围

## 局限与代价

### 1. Microsoft 生态的"金手铐"效应

Anders 在 Microsoft 工作了近 30 年（1996-至今）。这给了他巨大的资源和稳定性，但也意味着他的创造力被绑定在 Microsoft 的战略方向上。C# 和 TypeScript 的成功与 Microsoft 的平台战略密不可分——如果 Anders 在一家小公司或独立工作，这些语言可能不会有同样的采用率。

**启示**：大平台提供资源和分发渠道，但也限制了方向选择。如果你在大公司工作，要清醒地认识到：你的影响力有多少来自个人能力，有多少来自平台加持？

### 2. "向后兼容"的代价是技术债的累积

Anders 对向后兼容的坚持让 C# 和 TypeScript 获得了大规模采用，但也意味着语言中永远保留着早期的设计妥协。C# 中的 `var`、`dynamic`、`nullable reference types` 的"opt-in"设计，都是向后兼容约束下的妥协产物。TypeScript 中 `any` 类型的存在，也是对 JavaScript 遗留代码的妥协。

**启示**：渐进式改进的代价是永远无法"干净"地解决问题。如果你选择这条路，就要接受"不完美但可用"是常态，而不是追求理论上的完美。

### 3. 语言设计的"委员会化"风险

随着 C# 和 TypeScript 的用户规模扩大，设计决策越来越受到社区反馈和企业需求的影响。Anders 早期的"独裁式"设计（Turbo Pascal、Delphi 时代）逐渐让位于更民主但更缓慢的 RFC/提案流程。这保证了决策的合理性，但也可能稀释设计的锐度。

**启示**：当你的项目从小变大时，"一个人说了算"的效率优势会消失。要提前思考：如何在保持设计一致性的同时，容纳更多利益相关者的声音？

### 4. 个人生活与公众形象的缺失

与 Linus Torvalds 或 Elon Musk 不同，Anders 几乎没有公开的争议或个人生活曝光。他是一位极度低调的工程师，很少接受媒体采访，社交媒体活动极少。这种低调保护了他的专注力，但也意味着他的故事和方法论传播有限——很多年轻程序员知道 TypeScript，却不知道 Anders Hejlsberg。

**启示**：低调是一种选择，有其代价。如果你希望自己的技术理念产生更大影响，适度的公开表达和教学是必要的。

## 代表作品

- **Turbo Pascal**（1983）：革命性的 Pascal 编译器，以极快速度和极低价格颠覆市场
- **Delphi / Object Pascal**（1995）：将可视化编程与强类型系统结合的 Windows 开发环境
- **C#**（2000-至今）：.NET 生态的核心语言，引入 LINQ、async/await 等里程碑特性
- **TypeScript**（2012-至今）：JavaScript 的类型化超集，现代前端工程的事实标准
- **《The C# Programming Language》**：C# 语言规范参考书（与 Bill Joy、Joseph Albahari 合著）

## 延伸与关联

- **与 [[Bjarne Stroustrup]] 的对比**：两人都是丹麦人，都是语言设计巨匠。Bjarne 用 40 年维护 C++ 这一门语言，Anders 则在 40 年中创造了四门语言。Bjarne 的路径是"深度"，Anders 的路径是"广度中的深度"。
- **与 [[James Gosling]] 的对比**：C# 1.0 常被拿来与 Java 比较。两人面对的问题相似（企业级应用开发），但解决路径不同——Gosling 选择了 JVM 平台抽象，Anders 选择了语言特性的持续进化。
- **与 [[Guido van Rossum]] 的对比**：两人都强调"开发体验"优先于"执行性能"。但 Guido 的 Python 选择了"简单到不能再简单"，Anders 的 TypeScript 选择了"在复杂生态上叠加秩序"。
- **与 [[Linus Torvalds]] 的呼应**：两人都信奉"实用主义 > 理论优雅"。Linus 用 Linux 证明了"能跑比完美更重要"，Anders 用 TypeScript 证明了"渐进式改进比推倒重来更有效"。
- **与 [[做难事：突破舒适区]] 的呼应**：52 岁设计 TypeScript，在 JavaScript 这个"最混乱"的生态中建立类型秩序——这是 Anders 职业生涯中最大的"做难事"时刻。
- **与 [[第一性原理：从基本事实重新推导]] 的呼应**：TypeScript 的设计从第一性原理出发——"JavaScript 不会被替代"是基本事实，"大型项目需要类型安全"是基本需求，从这两个事实推导出"在 JS 之上加类型层"的解法。
