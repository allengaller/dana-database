# Michael Stonebraker：图灵奖得主，用 50 年证明「没有万能数据库」的学术创业者

> **"One size fits all is a myth. There is no single database system that can serve all needs well."**
> — Michael Stonebraker，多次学术演讲中的核心论点

> **"What's really important is not the technology, it's the idea."**
> — Michael Stonebraker，图灵奖演讲，2015

Michael Stonebraker（1943 年生于美国）是数据库领域最具影响力的计算机科学家之一，2014 年图灵奖得主。他的职业生涯跨越 50 年，核心贡献不是"一个数据库"，而是**一系列重新定义数据库设计哲学的系统和思想**：

- **Ingres**（1973）：第一个关系数据库管理系统之一，证明了关系模型的实用性
- **PostgreSQL**（1986）：Ingres 的继任者，如今全球最流行的开源关系数据库
- **Vertica**（2005）：列式分析数据库，开创了 OLAP 数据库的新范式
- **VoltDB / H-Store**（2007）：内存 OLTP 数据库，证明了"无锁"事务处理的可行性
- **SciDB**（2010）：面向科学计算的数组数据库

但 Stonebraker 最独特的不是他的技术贡献，而是他的**职业模式**：他是学术界最成功的"连续创业者"——在 MIT/Berkeley 做教授的同时，创办了 **8 家数据库公司**。他证明了**学术研究和商业实践不是对立的，而是可以互相加速的**。

我们研究他，是因为他展示了一种**极其罕见的职业路径**：50 年如一日地深耕一个领域（数据库），但从不满足于"一个答案"——他不断推翻自己之前的假设，不断提出"这个领域需要不同的方法"。他的"One Size Fits All"批判，不仅改变了数据库行业，也为所有技术人提供了一个思维范式：**当你发现"通用方案"时，问自己：它是否真的通用，还是只是"对大多数场景够用"？**

**但请注意**：Stonebraker 的路径高度依赖美国学术体制（终身教职保护、学术创业文化、MIT 品牌）。他的"学术创业者"模式在中国语境下面临不同的制度约束。我们提炼的是**"持续质疑 + 学术-商业双循环"的方法论**，而非简单复制他的职业路径。

---

## 为什么值得学

对 3-7 年技术人而言，Michael Stonebraker 的独特价值在于：

**第一，他展示了"深耕一个领域 50 年"的复利效应。** Stonebraker 从 1971 年开始研究数据库，到 2024 年仍然活跃。50 年的积累让他对数据库的理解达到了无人能及的深度——他不仅知道"现在的数据库怎么工作"，还知道"为什么是这样"、"之前尝试过什么"、"哪些路走不通"。这种深度不是读几篇论文能获得的，而是需要数十年的持续投入。

**第二，他的"One Size Fits All"批判是一种可迁移的思维工具。** Stonebraker 的核心论点是：**不存在一个数据库系统能同时做好 OLTP（事务处理）、OLAP（分析查询）、流处理、图查询、时序数据。** 每种工作负载有不同的最优设计。这个论点可以推广到所有技术领域：不存在"最好的编程语言"、"最好的架构"、"最好的框架"——只有"最适合你的工作负载的选择"。

**第三，他的"学术-创业双循环"模式展示了知识变现的另一种路径。** Stonebraker 不是"离开学术去创业"，而是"在学术中创业"——他的每家公司都源于一个学术论文，每个产品都是论文思想的商业化验证。这种模式让他既能保持学术深度，又能获得商业反馈。

## 关键转折与心法

### 转折一：从化学工程到计算机科学——意外的起点（1943-1971）

Michael Stonebraker 1943 年出生于美国马萨诸塞州。他最初在普林斯顿大学学习**化学工程**，1964 年获得学士学位。之后在 MIT 获得硕士和博士学位（1967、1971），方向是计算机科学。

这个"从化学工程到计算机科学"的转型看似偶然，但 Stonebraker 后来说，化学工程的训练给了他一种**系统思维**——理解复杂系统中各部分如何交互、如何在约束条件下优化整体性能。这种思维后来成为他数据库设计的核心方法论。

1971 年，Stonebraker 加入 UC Berkeley 计算机科学系，成为助理教授。当时，数据库领域正处于"前关系模型"时代——主流是 IBM 的层次模型（IMS）和 CODASYL 的网络模型。Edgar Codd 在 1970 年发表了关系模型论文，但几乎没有人相信"用表格和 SQL 就能管理数据"是可行的。

**心法提炼**：**跨领域背景是创新的催化剂。** Stonebraker 的化学工程训练让他用"系统优化"的视角看数据库，而不是被"计算机科学传统"束缚。**不要认为你的"非主流"背景是劣势——它可能是你看问题的独特视角。跨领域的知识迁移，往往是突破性创新的来源。**

---

### 转折二：Ingres 与关系数据库的"证明之战"（1973-1985）

1973 年，Stonebraker 在 Berkeley 启动了 **Ingres**（INteractive Graphics REtrieval System）项目。这是学术界第一个认真实现关系数据库管理系统的尝试。

当时，IBM 正在开发 System R（SQL 的发源地），但 IBM 的策略是把关系数据库作为"未来产品"慢慢推进——因为 IMS（层次数据库）每年给 IBM 带来数十亿美元收入，IBM 没有动力快速颠覆自己。

Stonebraker 看到了这个"创新者的窘境"，决定用 Ingres 证明：**关系数据库不仅理论上优雅，实际上也能用。** Ingres 的关键创新包括：

- **查询优化器**：自动将 SQL 转换为高效的执行计划
- **视图更新**：支持对视图的更新操作
- **规则系统**：用规则实现完整性约束和触发器
- **多用户并发控制**：支持多用户同时访问

Ingres 在 1980 年代成为学术界最广泛使用的数据库系统，并催生了多家公司（Ingres Corporation、Illustra 等）。更重要的是，Ingres 的代码被公开，直接影响了 **Sybase、Microsoft SQL Server、NonStop SQL** 等商业数据库的设计。

1985 年，Stonebraker 离开 Berkeley 回到 MIT，开始思考 Ingres 的"下一代"应该是什么。

**心法提炼**：**当巨头因为"现有业务"而犹豫时，就是颠覆者的窗口。** IBM 不是不知道关系数据库好，而是"现有业务太好"导致它不敢快速转型。Stonebraker 利用了这个窗口。**在你的领域中，哪些"巨头"因为现有业务的成功而不敢创新？那些被忽视的方向，可能就是你的机会。**

---

### 转折三：PostgreSQL 与"可扩展数据库"的愿景（1986-1996）

回到 MIT 后，Stonebraker 启动了 **Post-Ingres** 项目（后来改名为 **PostgreSQL**）。他的核心问题是：Ingres 证明了关系模型可行，但关系模型本身有局限——它不支持复杂数据类型（数组、JSON、地理空间数据）、不支持用户自定义函数、不支持继承。

PostgreSQL 的核心创新是**可扩展性**：
- **用户自定义数据类型**：你可以定义自己的数据类型（如地理坐标、网络地址）
- **用户自定义函数**：你可以用多种语言（C、Python、Perl）写数据库函数
- **用户自定义操作符**：你可以定义自己的操作符（如"包含"、"重叠"）
- **继承**：表可以继承其他表的 schema

这个设计哲学是：**数据库不应该是一个"封闭的系统"，而应该是一个"可扩展的平台"。** 你不需要等数据库厂商添加你需要的功能——你可以自己扩展它。

PostgreSQL 在 1996 年发布了第一个开源版本。Stonebraker 随后将注意力转向了其他项目，但 PostgreSQL 的开源社区接管了后续开发。到 2024 年，PostgreSQL 已经成为全球最流行的开源关系数据库，被 Apple、Instagram、Reddit 等公司广泛使用。

**心法提炼**：**最好的系统设计是"可扩展的平台"，而不是"完整的产品"。** Stonebraker 没有试图在 PostgreSQL 中实现所有功能，而是设计了一个"让你自己添加功能"的框架。这种"平台思维"比"产品思维"有更长的生命力——产品会过时，但平台可以不断进化。**在你的系统设计中，问自己：我是在做一个"封闭的产品"还是一个"开放的平台"？后者虽然短期更难，但长期更有价值。**

---

### 转折四："One Size Fits All"批判与专用数据库浪潮（2005-2015）

2005 年前后，Stonebraker 发表了一系列影响深远的论文和演讲，核心论点是：

> **"传统数据库（如 Oracle、MySQL、PostgreSQL）试图用一个系统服务所有工作负载，但这是错误的。OLTP、OLAP、流处理、图查询、时序数据——每种工作负载需要完全不同的架构。"**

这不是空谈。Stonebraker 用**实际行动**证明了这个论点——他创办了一系列"专用数据库"公司：

- **Vertica**（2005）：列式存储 + 无索引设计，专为 OLAP 分析优化。比传统行式数据库快 10-100 倍。2011 年被 HP 收购。
- **VoltDB / H-Store**（2007）：纯内存 + 单线程分区 + 无锁设计，专为高吞吐 OLTP 优化。证明了"传统数据库 90% 的时间花在无用功上"（锁等待、日志写入、缓冲区管理）。
- **SciDB**（2010）：数组数据库，专为科学计算（天文、基因组、气候模拟）设计。
- **Tamr**（2013）：数据整合和主数据管理平台。

每家公司都源于一个核心洞察：**对于特定工作负载，通用数据库的"通用性"是负担，不是优势。** 去掉不需要的功能，针对特定工作负载深度优化，可以获得数量级的性能提升。

2014 年，Stonebraker 获得**图灵奖**，表彰他"对现代数据库系统概念和实践的基础性贡献"。

**心法提炼**：**当你发现"通用方案"时，问：它是否真的通用，还是只是"对大多数场景够用"？** Stonebraker 的"One Size Fits All"批判不是"通用方案不好"，而是"通用方案在某些场景下是灾难性的"。**在你的技术选型中，不要被"通用"迷惑。问自己：我的工作负载的特殊性是什么？通用方案在哪些方面为"通用性"付出了我不需要的代价？是否有专用方案能做得更好？**

---

### 转折五：80 岁仍然在创业——学术创业者的终身模式（2015-至今）

获得图灵奖后，72 岁的 Stonebraker 没有退休。他继续在 MIT 做研究、继续创业、继续在学术会议上发表尖锐观点。

2015-2024 年间，他的关注点转向了：
- **数据整合**（Tamr）：企业数据孤岛问题
- **数据库基准测试的批判**：他认为 TPC 基准测试"测量的是错误的东西"
- **AI 与数据库的交叉**：向量数据库、AI-native 数据库
- **数据库教育**：他持续在 MIT 教授数据库课程，培养下一代数据库研究者

到 2024 年，81 岁的 Stonebraker 仍然活跃。他的职业生涯证明了一个观点：**学术创造力没有"退休年龄"。** 只要保持好奇心、保持对问题的敏感、保持动手实现的意愿，创造力可以持续数十年。

**心法提炼**：**创造力不衰减，衰减的是好奇心。** Stonebraker 80 岁仍然在创业、仍然在写论文、仍然在课堂上和学生辩论。他的"长寿"不是因为他"保养得好"，而是因为他**从未停止对数据库问题的好奇**。**在你的职业发展中，不要设定"退休年龄"。只要你仍然对问题好奇、仍然想动手解决，你就仍然在"创造价值"。**

## 核心可学习点

### 1. "One Size Fits All"思维——质疑通用方案

Stonebraker 的核心思维工具是：**当所有人都在用"通用方案"时，问"它真的通用吗？"** 通用方案的代价是：为了覆盖所有场景，它在每个场景上都不是最优的。

**行动建议**：下次做技术选型时，不要默认选"最流行的"或"最通用的"。列出你的工作负载的具体特征（读写比、数据量、延迟要求、一致性要求），然后问：有没有专门为这种工作负载设计的方案？通用方案在哪些方面为"通用性"付出了我不需要的代价？

### 2. "学术-商业双循环"——让研究和实践互相加速

Stonebraker 的每家公司都源于一个学术论文，每个产品都是论文思想的商业化验证。学术给他"深度"（理解问题的本质），商业给他"反馈"（验证想法是否真的有用）。

**行动建议**：在你的工作中，建立"学习-实践"的双循环。不要只"学"不"做"（纯理论），也不要只"做"不"学"（纯经验）。每学一个新概念，尝试在实际项目中验证它；每遇到一个实际问题，去查找相关的理论和研究。

### 3. "推翻自己"的勇气——从 Ingres 到 PostgreSQL 到 Vertica

Stonebraker 的职业生涯是不断"推翻自己"的过程：Ingres 证明了关系模型，PostgreSQL 扩展了关系模型，Vertica 说"关系模型对分析场景是错的"，VoltDB 说"传统 OLTP 架构 90% 是浪费"。他从不执着于"我之前的贡献"。

**行动建议**：定期审视你之前的技术决策和信念。问自己：我是否因为"我之前选了 X"就拒绝考虑 Y？我是否因为"我擅长 X"就忽视 Y 的价值？真正的专家不是"永远正确的人"，而是"愿意推翻自己的人"。

### 4. "动手实现"——论文不够，要做出来

Stonebraker 不是纯理论家。他的每个想法都有对应的系统实现：Ingres、PostgreSQL、Vertica、VoltDB、SciDB。他认为：**一个没有实现的数据库想法，只是一个"可能正确"的假设。只有做出来、跑起来、用真实数据测试，才能证明它真的有效。**

**行动建议**：不要只停留在"想法"层面。当你有一个技术想法时，做一个最小实现——不需要完美，不需要生产级，只需要能跑、能验证核心假设。一个跑起来的原型比十篇 PPT 更有说服力。

## 今天就可以开始的 3 件事

1. **了解 PostgreSQL 的"可扩展性"设计**
   - 访问 postgresql.org，阅读 "About" 页面
   - 重点理解：用户自定义类型、自定义函数、自定义操作符
   - 思考：你的项目中是否有"需要数据库扩展"的场景？

2. **阅读 Stonebraker 的 "One Size Fits All" 相关论文**
   - 搜索 "Stonebraker One Size Fits All 2007"
   - 理解他为什么认为 OLTP 和 OLAP 需要不同的架构
   - 思考：你的系统中是否在用"通用方案"处理"专用工作负载"？

3. **对你的数据库做一次"工作负载分析"**
   - 你的数据库主要处理什么类型的查询？（点查？范围扫描？聚合分析？）
   - 读写比是多少？数据量多大？延迟要求是什么？
   - 基于这些特征，你当前的数据库选择是否最优？

## 局限与代价

### 1. "连续创业"的精力分散

Stonebraker 创办了 8 家公司，这意味着他的注意力被分散在多个方向上。每家公司都需要时间、精力、和关注度。虽然每家公司都源于一个清晰的学术洞察，但"同时推进多个创业"不可避免地意味着每个项目获得的关注有限。

**启示**：连续创业有其代价——你可能无法在任何一个方向上做到"极致深度"。如果你选择"广度"（多个项目），就要接受每个项目的深度可能不如"只做一个项目"的人。这是一个真实的 trade-off，不是"更努力"就能解决的。

### 2. 学术创业的制度依赖

Stonebraker 的"学术创业者"模式高度依赖美国学术体制：终身教职保护（让他可以在创业失败后回到学术）、MIT 的品牌效应（让他的公司天然有可信度）、学术创业文化（MIT 鼓励教授创业）。这些条件在其他国家和其他学术体制中不一定存在。

**启示**：学习 Stonebraker 的"学术-商业双循环"方法论，但要根据自己的制度环境调整实现方式。在中国，学术和创业之间的流动性和制度支持与美国不同，需要找到适合自己的路径。

### 3. "专用数据库"的碎片化风险

Stonebraker 的"One Size Fits All"批判推动了"专用数据库"的繁荣，但也带来了碎片化风险：企业可能需要同时使用 OLTP 数据库、OLAP 数据库、图数据库、时序数据库、向量数据库——每种都需要不同的运维技能、不同的监控工具、不同的数据同步机制。

**启示**：专用方案有性能优势，但也有复杂性成本。在选择专用方案时，要评估"性能提升"是否值得"额外的运维复杂性"。有时候，一个"够用"的通用方案比一个"最优"的专用方案更实际。

## 代表作品

- **Ingres**（1973-1985）：第一个学术关系数据库系统，影响了 Sybase、SQL Server 等商业产品
- **PostgreSQL**（1986-至今）：全球最流行的开源关系数据库，Apple、Instagram、Reddit 等使用
- **Vertica**（2005-2011）：列式分析数据库，被 HP 收购
- **VoltDB / H-Store**（2007-至今）：内存 OLTP 数据库，证明了无锁事务处理的可行性
- **SciDB**（2010）：面向科学计算的数组数据库
- **Tamr**（2013）：数据整合和主数据管理平台
- **"One Size Fits All: An Idea Whose Time Has Come and Gone"**（2005）：数据库领域引用量最高的论文之一
- **图灵奖**（2014）：表彰对现代数据库系统的基础性贡献

## 延伸与关联

- **与 [[Donald Knuth]] 的对比**：两人都是"学术深度 + 系统实现"的典范。Knuth 用 TAOCP 和 TeX 证明了"算法可以被精确描述和实现"，Stonebraker 用 Ingres/PostgreSQL 证明了"关系模型可以被高效实现"。两人都展示了"理论 + 实现"的结合力量。
- **与 [[Jeff Dean]] 的对比**：Jeff Dean 在 Google 构建了 BigTable、Spanner、TensorFlow；Stonebraker 在学术界构建了 Ingres、PostgreSQL、Vertica。两人都在"数据管理系统"领域做出了核心贡献，但路径不同：Dean 是"工业界规模"，Stonebraker 是"学术界深度 + 创业验证"。
- **与 [[Linus Torvalds]] 的对比**：两人都创造了影响全球的基础设施（Linux vs PostgreSQL），但方式不同。Linus 是"一个人开始，社区接管"，Stonebraker 是"学术项目，商业化验证，社区接管"。
- **与 [[第一性原理：从基本事实重新推导]] 的呼应**：Stonebraker 的"One Size Fits All"批判就是第一性原理的应用——回到基本事实（"OLTP 和 OLAP 的访问模式完全不同"），然后推导出"它们需要不同的架构"。
- **与 [[做难事：突破舒适区]] 的呼应**：Stonebraker 不断推翻自己之前的贡献——从 Ingres 到 PostgreSQL 到 Vertica 到 VoltDB，每次都是"否定之前的假设，重新开始"。这种"自我否定"的勇气，是"做难事"的极致体现。
- **与 [[系统思维与全链路视角]] 的呼应**：Stonebraker 的数据库设计始终关注"全链路"——从查询解析、优化、执行、存储、并发控制到恢复。他不是只优化一个环节，而是理解整个系统如何协同工作。
