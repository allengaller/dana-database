# Bjarne Stroustrup：C++ 之父，用四十年守护一门语言的演化

> **"C++ is a horrible language. It's made more horrible by the fact that a lot of substandard programmers use it, to the point where it's much much easier to generate total and utter crap with it."**
> — Linus Torvalds（引述此言是为了展示 Stroustrup 面对批评时的态度）

> **"I have always wished that my computer would be as easy to use as my telephone. My wish has come true. I no longer know how to use my telephone."**
> — Bjarne Stroustrup

Bjarne Stroustrup（1950 年生于丹麦奥胡斯）是 C++ 编程语言的创造者和持续守护者。从 1979 年在贝尔实验室开始设计 "C with Classes"，到 2024 年仍在推动 C++ 的现代化（C++23、C++26），他用了超过四十五年时间维护和发展同一门语言。

C++ 是当今世界上使用最广泛的系统编程语言之一：操作系统（Windows、macOS 内核）、浏览器（Chrome、Firefox）、游戏引擎（Unreal Engine）、数据库（MySQL、MongoDB）、金融交易系统、嵌入式系统、航天器控制软件——几乎所有对性能有极致要求的系统都使用 C++。全球估计有超过 400 万 C++ 开发者。

但 Stroustrup 的故事远不止"发明了一门语言"。他的独特之处在于：**他在四十五年中持续守护一门语言的演化方向，在"向后兼容"与"现代化"之间走钢丝，在"性能"与"安全"之间寻找平衡，在"学术理想"与"工业现实"之间架设桥梁。** 这种长期守护一个超大规模技术项目的经验，在技术史上几乎独一无二。

---

## 为什么值得学

对 3-7 年技术人而言，Bjarne Stroustrup 的独特价值在于：

**第一，他展示了"长期主义"在技术领域的极致形态。** 大多数技术人每 3-5 年换一个技术栈或方向，而 Stroustrup 用四十五年守护同一门语言。这不是因为缺乏创造力——C++ 从 C with Classes 到 C++98 到 C++11 到 C++20，每一次重大版本都是深刻的设计创新。他的长期主义是"在同一领域内持续深化"，而不是"重复做同一件事"。

**第二，他展示了如何在"向后兼容"的约束下持续创新。** C++ 必须兼容 1980 年代的 C 代码，必须兼容 1990 年代的 C++98 代码，必须兼容数百万企业项目的既有投资。在这个约束下，Stroustrup 仍然引入了模板元编程、RAII、移动语义、概念（Concepts）、模块（Modules）等革命性特性。这种"戴着镣铐跳舞"的能力，对所有维护遗留系统的工程师都有深刻启发。

**第三，他是"学术-工业"桥梁的典范。** Stroustrup 拥有剑桥大学博士学位，在贝尔实验室做了 25 年研究，后来在 Texas A&M 和 Columbia 大学任教，同时在 Morgan Stanley 和 Standard C++ Foundation 工作。他始终在学术严谨性和工业实用性之间寻找平衡，这种双重视角让 C++ 既有理论深度又有实际价值。

## 关键转折与心法

### 转折一：在贝尔实验室用 Simula 写分布式系统（1975-1979）——从挫败中诞生新语言

1975 年，Stroustrup 从剑桥大学获得博士学位后，加入贝尔实验室（Bell Labs）的计算科学研究部门。他的第一个项目是用 **Simula** 语言编写分布式操作系统。

Simula 是世界上第一门面向对象语言，设计优雅、抽象能力强。但 Stroustrup 发现一个致命问题：**Simula 太慢了。** 他的程序在 Simula 中运行速度只有用 BCPL（C 的前身）编写的十分之一。对于一个需要处理大量并发事件的分布式系统来说，这种性能差距是不可接受的。

他被迫用 BCPL 重写了整个系统。BCPL 性能极好，但缺乏 Simula 的抽象能力——没有类、没有继承、没有对象。Stroustrup 不得不在代码中手动模拟面向对象的结构。

这次经历让他产生了一个核心洞察：**能不能把 Simula 的抽象能力和 C 的性能结合起来？** 这就是 "C with Classes" 的起源——在 C 语言上添加类、继承、虚函数等面向对象特性，同时保持 C 的零开销性能。

**心法提炼**：**最好的设计往往来自两种对立需求的碰撞。** Stroustrup 不是凭空设计了 C++，而是在"Simula 的优雅"和"BCPL/C 的性能"之间找到了交汇点。当你面对两个看似矛盾的需求时，不要简单地选择其中一个——问自己：有没有一种设计能同时满足两者？

---

### 转折二：C with Classes 到 C++（1979-1985）——从内部工具到公开发布

1979 年，Stroustrup 开始在贝尔实验室内部开发 "C with Classes"。最初，它只是一个预处理器（Cfront），把"带类的 C"代码转换为标准 C 代码。

1983 年，语言被正式命名为 "C++"（"++"是 C 语言中的自增运算符，暗示它是 C 的"进化"）。1985 年，Stroustrup 出版了 **《The C++ Programming Language》** 第一版，同时 C++ 编译器开始商业化发布。

C++ 早期的关键设计决策包括：
- **多重继承**：一个类可以继承多个基类（比 Java 的单继承更灵活，但也更复杂）
- **虚函数**：运行时多态的基础
- **运算符重载**：允许用户自定义类型使用 +、-、[] 等运算符
- **模板**：泛型编程的基础（后来成为 C++ 最强大的特性之一）
- **异常处理**：结构化的错误处理机制
- **RAII（Resource Acquisition Is Initialization）**：用对象生命周期管理资源

这些特性让 C++ 成为了一门"多范式"语言——它同时支持过程式、面向对象、泛型编程，后来还加入了函数式编程元素。

**心法提炼**：**不要等到"完美"才发布。** C++ 1.0 远不是最终形态——它没有模板、没有异常、没有 STL。但 Stroustrup 选择了尽早发布、获取反馈、持续迭代。如果等到所有特性都设计好再发布，C++ 可能永远不会存在。**先发布一个"足够好"的版本，然后让真实用户帮你发现设计中的问题。**

---

### 转折三：C++98 标准化与 STL 的加入（1990-1998）——从个人项目到国际标准

1990 年代，C++ 的使用量爆炸式增长，但不同编译器的实现差异导致了严重的兼容性问题。Stroustrup 意识到，C++ 需要一个正式的国际标准。

1998 年，ISO/IEC 14882:1998（即 C++98）正式发布。这是 C++ 历史上的第一个国际标准。标准化过程中最重要的事件是 **STL（Standard Template Library）** 的加入。

STL 由 Alexander Stepanov 设计，基于"泛型编程"理念：用模板实现通用容器（vector、map、list）和算法（sort、find、transform）。STL 的加入让 C++ 从"带类的 C"进化为一门真正支持泛型编程的语言。

Stroustrup 在标准化过程中的角色是"技术方向的守护者"。他不做所有决策，但确保标准不会偏离 C++ 的核心哲学：**零开销抽象、多范式支持、与 C 的兼容性。**

**心法提炼**：**当你的创造物从"个人项目"变成"行业标准"时，你的角色必须从"设计者"转变为"守护者"。** 标准化意味着你不再能单方面做决策，你需要说服委员会、平衡各方利益、接受妥协。但核心设计哲学不能妥协——Stroustrup 在标准化过程中坚守了"零开销抽象"原则，即使这意味着拒绝某些"方便但有性能代价"的特性。

---

### 转折四：C++11 的"重生"——十年沉寂后的革命性更新（2003-2011）

C++98 之后，C++ 经历了一段"沉寂期"。C++03 只是一个小的修正版本，而 C++0x（后来的 C++11）的标准化过程异常漫长——从 2003 年开始讨论，到 2011 年才正式发布。

但 C++11 是一次真正的革命。它引入了：
- **auto 类型推断**：减少冗余的类型声明
- **Lambda 表达式**：匿名函数，让函数式编程成为可能
- **右值引用和移动语义**：消除不必要的深拷贝，大幅提升性能
- **智能指针（unique_ptr、shared_ptr）**：让 RAII 更易用，减少内存泄漏
- **constexpr**：编译时计算
- **范围 for 循环**：简化容器遍历
- **nullptr**：替代危险的 NULL/0

Stroustrup 将 C++11 描述为"一门新语言"——它保留了 C++98 的所有代码兼容性，但编程风格发生了根本性变化。C++11 之后的 C++ 代码比 C++98 时代更安全、更简洁、更现代。

**心法提炼**：**长期维护一个项目不意味着"小修小补"。在正确的时机，可以做革命性的更新——前提是不破坏向后兼容。** C++11 证明了：你可以在保持 30 年代码兼容的同时，彻底改变语言的编程范式。关键是"增量式革命"——新特性是 opt-in 的，旧代码继续工作，新代码享受新特性。

---

### 转折五：C++20/23 与"让 C++ 变安全"的持续努力（2017-至今）

2017 年后，C++ 的标准化周期稳定为每三年一个版本（C++17、C++20、C++23、C++26）。Stroustrup 虽然不再主导每个细节，但仍然深度参与方向性决策。

C++20 引入了四个"大特性"：
- **Concepts（概念）**：对模板参数的约束，让模板错误信息更可读
- **Modules（模块）**：替代 40 年历史的 #include 机制
- **Coroutines（协程）**：原生异步编程支持
- **Ranges（范围库）**：更安全的容器操作

同时，Stroustrup 在 2022 年发表了 **"Safety" 系列论文**，回应了 NSA、CISA 等机构对 C++ "内存不安全"的批评。他的论点是：C++ 可以通过 Guidelines（编码指南）、静态分析、和现代特性（智能指针、span、string_view）来实现内存安全，而不需要像 Rust 那样引入全新的所有权系统。

这场"C++ vs Rust"的辩论是 2020 年代编程语言界最重要的讨论之一。Stroustrup 的立场是：**不要抛弃 40 年的代码投资，而是在现有基础上渐进式地提高安全性。**

**心法提炼**：**面对"你的技术已经过时"的批评，最好的回应不是辩护，而是展示持续的进化。** Stroustrup 没有说"C++ 不需要改进"，而是用 C++20/23 的实际特性证明了 C++ 仍然在进化。同时，他也没有完全否定批评者——他承认 C++ 的安全性确实需要改进，只是选择了"渐进式改进"而非"推倒重来"的路径。

## 核心可学习点

### 1. "零开销抽象"——不为不使用的东西付费

C++ 的核心设计原则是"零开销抽象"（Zero-overhead Abstraction）：如果你不使用某个特性，它不应该产生任何运行时开销；如果你使用某个特性，它不应该比手写底层代码更慢。

这个原则让 C++ 在保持高级抽象能力的同时，性能与 C 相当。模板在编译时展开，虚函数只在需要多态时使用，RAII 不产生额外的堆分配。

**行动建议**：在设计框架或库时，问自己：用户如果不使用某个特性，是否会为它付出代价（启动时间、内存占用、运行时检查）？如果是，考虑把它变成 opt-in 而不是默认行为。

### 2. 多范式思维——不要强迫用户进入单一编程模型

C++ 同时支持过程式、面向对象、泛型、函数式编程。Stroustrup 认为：**不同的问题适合不同的编程范式，一门好的系统语言不应该强迫用户只用一种方式思考。**

这与 Java（强制一切皆对象）和 Haskell（强制纯函数式）形成对比。C++ 的灵活性让它能适应从嵌入式系统到游戏引擎到金融交易的广泛场景。

**行动建议**：在设计 API 或框架时，不要强迫用户采用你偏好的编程范式。提供多种使用方式，让不同背景的开发者都能找到舒适的使用模式。

### 3. 向后兼容是承诺，不是技术债

C++ 必须能编译 1985 年的代码。这不是因为 Stroustrup 不知道"推倒重来"更简单，而是因为他理解：**数百万企业项目的代码投资不能因为语言升级而作废。** 向后兼容是语言对用户的承诺，是信任的基础。

**行动建议**：如果你维护一个被他人依赖的库或 API，把向后兼容当作核心承诺。每次破坏性变更都要提供迁移工具、兼容层、和充分的过渡期。

### 4. 用"编码指南"弥补语言设计的不足

Stroustrup 在 2015 年发起了 **C++ Core Guidelines**——一份持续更新的 C++ 最佳实践指南。它不是语言标准的一部分，但指导开发者如何使用现代 C++ 特性来避免常见错误。

这体现了一个重要洞察：**语言设计不能解决所有问题，教育和指南同样重要。** 即使是最安全的语言，如果开发者不知道最佳实践，也会写出不安全的代码。

**行动建议**：在你的团队中，除了代码审查，还要维护一份"编码指南"或"最佳实践文档"。它应该随项目演化，而不是写一次就放在那里吃灰。

### 5. 学术严谨性与工业实用性的平衡

Stroustrup 的每一个设计决策都有学术论文支撑（模板元编程、RAII、Concepts），但同时都有明确的工业应用场景。他从不为了"理论优雅"而添加没有实际用途的特性，也从不为了"方便"而牺牲理论正确性。

**行动建议**：在做技术决策时，既要有理论依据（为什么这个方案是正确的），也要有实际验证（这个方案在真实场景中是否有效）。两者缺一不可。

## 今天就可以开始的 3 件事

1. **阅读 C++ Core Guidelines 的前 10 条规则**
   - 访问 https://isocpp.github.io/CppCoreGuidelines/
   - 重点阅读 I（Introduction）、P（Philosophy）部分
   - 即使你不写 C++，其中关于"资源管理"、"接口设计"、"错误处理"的原则也适用于任何语言

2. **理解 RAII 模式并迁移到你的语言中**
   - RAII 的核心思想：用对象的生命周期（构造/析构）来管理资源（内存、文件句柄、锁）
   - 在 Python 中对应 `with` 语句，在 Go 中对应 `defer`，在 Rust 中对应 `Drop` trait
   - 在你的项目中找一个"资源泄漏"风险点，用 RAII 思维重新设计

3. **对比 C++ 和 Rust 的内存安全策略**
   - C++ 策略：智能指针 + 编码指南 + 静态分析（渐进式安全）
   - Rust 策略：所有权系统 + 借用检查器（编译时强制安全）
   - 思考：在你的项目中，"渐进式改进"和"强制约束"哪种策略更适合你的团队？

## 局限与代价

### 1. C++ 的复杂性是真实的

C++ 是当今最复杂的编程语言之一。它的标准文档超过 1800 页，特性组合爆炸，模板错误信息令人绝望。Stroustrup 自己承认："C++ 确实太复杂了，但我不知道如何在保持向后兼容的同时简化它。"

这种复杂性有真实的代价：学习曲线陡峭、新手容易犯错、代码审查成本高。Rust、Go 等新语言的崛起，部分原因就是对 C++ 复杂性的反叛。

**启示**：长期演化的系统不可避免地会积累复杂性。如果你从一开始就设计一个"最小核心"，可能比"不断添加特性"更有利于长期健康。但如果你已经在一个复杂系统中，渐进式简化比推倒重来更现实。

### 2. "向后兼容"的代价是永远无法移除错误设计

C++ 中有一些被广泛认为是设计错误的特性（如隐式转换规则、某些继承语义），但因为向后兼容承诺，它们永远无法被移除。Stroustrup 只能添加新特性来"绕过"旧问题，而不能直接修复。

**启示**：向后兼容是一把双刃剑。它保护了用户投资，但也意味着你必须永远与早期的设计妥协共存。在做早期设计决策时，要格外慎重——因为一旦发布，你可能永远无法撤回。

### 3. 安全性辩论中的"渐进派"困境

在 C++ vs Rust 的安全性辩论中，Stroustrup 的"渐进式改进"立场面临一个根本性挑战：**如果现有代码库中有数十亿行不安全的 C++ 代码，"指南"和"最佳实践"真的能让它们变安全吗？** Rust 的支持者认为，只有编译器强制的安全保证才是可靠的，"指南"只是建议，可以被忽略。

**启示**：渐进式改进在"新项目"中有效，但在"遗留代码"中可能不够。有时候，承认"旧代码无法被修复，只能被替换"是更诚实的选择。

### 4. 个人影响力与社区治理的张力

Stroustrup 在 C++ 标准化委员会中拥有巨大的个人影响力，但 C++ 的决策最终由委员会投票决定。这导致了一些他反对的特性被加入（如某些异常处理语义），也导致了一些他支持的特性被延迟（Concepts 从 2003 年讨论到 2020 年才进入标准）。

**启示**：当你的项目从"个人创造"变成"社区治理"时，你的影响力会从"决策权"变成"说服力"。要学会在没有最终决定权的情况下影响方向。

- **《The C++ Programming Language》**（1985-2013，四版）：C++ 的权威参考书
- **《The Design and Evolution of C++》**（1994）：C++ 设计决策的历史记录

- **Cfront**（1983）：第一个 C++ 编译器（将 C++ 转换为 C）

## 延伸与关联

- **与 [[Anders Hejlsberg]] 的对比**：两人都是丹麦人，都是语言设计巨匠。Stroustrup 用 45 年守护一门语言（深度），Hejlsberg 在 40 年中创造了四门语言（广度）。Stroustrup 的路径是"在一门语言中持续进化"，Hejlsberg 的路径是"在新语言中应用积累的经验"。
- **与 [[James Gosling]] 的对比**：Java 的设计在很多方面是对 C++ 的"反叛"。Gosling 去掉了 C++ 中他认为危险的特性，Stroustrup 则保留了这些特性但提供了更安全的替代方案。两人代表了"通过禁止来保证安全"vs"通过教育来引导安全"两种哲学。
- **与 [[Ken Thompson]] / [[Rob Pike]] 的传承**：C++ 建立在 C 之上，而 C 是 Thompson 和 Ritchie 在贝尔实验室创造的。Stroustrup 在同一个实验室工作，直接继承了 C 的设计哲学。Rob Pike 后来用 Go 语言"反叛"了 C++ 的复杂性。
- **与 [[做难事：突破舒适区]] 的呼应**：45 年维护一门语言，在向后兼容的约束下持续创新，面对"你的语言已经过时"的批评仍然坚持进化——这是"做难事"的极致体现。
- **与 [[第一性原理：从基本事实重新推导]] 的呼应**：C++ 的设计从第一性原理出发——"程序员需要高级抽象"和"抽象不能有性能代价"是两个基本事实，从这两个事实推导出"零开销抽象"的设计原则。
