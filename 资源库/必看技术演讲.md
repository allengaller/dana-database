# 必看技术演讲：改变思维方式的高质量 Talk 精选

> 一个好的技术演讲，不是教你「怎么用某个工具」，而是改变你「看问题的方式」。
> 以下每一个 Talk，都值得你关掉手机、打开全屏、认真看完。

---

## 如何使用这份清单

### 观看策略

1. **不要倍速**：这些演讲的价值不在于信息密度，而在于思维方式的传递。1.5x 速会让你错过最关键的停顿和强调。
2. **看完后写 3 句话总结**：用自己的话写下「这个演讲改变了我什么认知」。写不出来 = 没真正吸收。
3. **一个主题看完后做对比**：比如看完 Rich Hickey 的 "Simple Made Easy" 后，再看 Bret Victor 的 "Inventing on Principle"，思考他们对「好软件」的定义有何异同。
4. **分享给团队**：好的演讲是团队文化建设的最低成本工具。每周在群里分享一个，比开一次无效会议有价值 100 倍。
5. **做笔记用时间戳**：在关键观点处记录时间戳（如 `[23:15]`），方便回看和引用。

### 从演讲中学习的方法论

详细的「如何从技术演讲中高效学习」方法论，参见 [[如何做技术演讲]] 中的「作为观众」章节。核心原则：

- **带着问题看**：看之前问自己「我希望从这个演讲中获得什么？」
- **关注「为什么」而非「是什么」**：演讲者选择做什么不重要，重要的是他为什么这样选择。
- **关注演讲者的思维模型**：每个优秀演讲者都有一个底层的思维框架，试着识别它。
- **不要只收藏不看**：「稍后再看」列表是技术人的坟场。每周固定 2 小时看一个。

## 一、编程哲学

这些演讲不教你写代码，但会改变你对「什么是好代码」的定义。

### 1. Simple Made Easy

- **演讲者**：Rich Hickey（Clojure 语言创始人）
- **年份**：2011（Strange Loop 大会）
- **时长**：61 分钟
- **一句话收获**：「简单」（simple，一个职责）和「容易」（easy，熟悉）是完全不同的概念。大多数程序员追求「容易」却牺牲了「简单」，这才是系统越来越复杂的根源。
- **核心观点**：
  - 复杂性不是 bug 多，而是「交织」（complecting）——把不相关的东西绑在一起
  - 面向对象把状态和行为绑在一起，是一种 complecting
  - 函数式编程的核心价值不是「没有副作用」，而是「把东西分开」
  - 设计的目标应该是「简单」：每个组件只做一件事，组件之间松耦合
- **为什么必看**：这是过去 15 年影响力最大的编程哲学演讲。它重新定义了「好设计」的标准，影响了无数架构师和语言设计者。看完之后，你看代码的眼光会永久改变。
- **观看建议**：前 20 分钟是定义和铺垫，核心论证在 20-45 分钟。如果时间紧，从 15:00 开始看。
- **链接**：YouTube 搜索 "Rich Hickey Simple Made Easy Strange Loop 2011"

### 2. Inventing on Principle

- **演讲者**：Bret Victor（前 Apple 工程师，交互设计先驱）
- **年份**：2012（CUFP 大会）
- **时长**：54 分钟
- **一句话收获**：创造者需要「即时反馈」——当你改变代码时，应该立刻看到结果。大多数编程环境剥夺了这种反馈，扼杀了创造力。
- **核心观点**：
  - 编程应该是「可触摸的」：改一行代码，立刻看到效果
  - 他现场演示了一个「实时编程环境」：画布上的图形随代码变化实时改变
  - 更深层的观点：每个创造者都应该有一个「指导原则」（principle），并围绕它设计工具
  - 他的原则是：「创造者必须能够即时看到他们创造的东西」
- **为什么必看**：Bret Victor 的演讲不是「技术分享」，而是「对未来的想象」。他演示的工具大多没有商业化，但他的思想直接影响了 React Hot Reload、Observable、Figma 等产品。这个演讲会重新点燃你对「编程可以是什么样」的想象力。
- **观看建议**：全程无尿点，建议一次看完。特别注意 18:00-35:00 的现场演示部分。
- **链接**：YouTube 搜索 "Bret Victor Inventing on Principle"

### 3. The Value of Values

- **演讲者**：Rich Hickey
- **年份**：2012（Strange Loop 大会）
- **时长**：58 分钟
- **一句话收获**：「值」（value，不可变的、确定的数据）比「状态」（state，随时间变化的引用）更容易推理、测试和并行化。大多数系统bug来自对「值」和「身份」的混淆。
- **核心观点**：
  - 值是不可变的：数字 42 永远是 42，不会变成 43
  - 状态是对值的引用：变量 x 先指向 42，后指向 43
  - 大多数编程错误来自把「状态」当「值」用
  - 不可变数据结构不是性能敌人，而是正确性的朋友
- **为什么必看**：如果你看完 "Simple Made Easy" 觉得「有道理但不够具体」，这个演讲是完美的补充。它把「为什么不可变性重要」讲到了工程实践层面。
- **链接**：YouTube 搜索 "Rich Hickey The Value of Values"

## 二、系统设计

这些演讲帮你理解「如何在真实约束下构建大规模系统」。

### 4. Building Software Systems at Google and Lessons Learned

- **演讲者**：Jeff Dean（Google 高级研究员，MapReduce/TensorFlow/Spanner 核心设计者）
- **年份**：2010（Stanford 演讲）/ 2022（更新版）
- **时长**：75 分钟
- **一句话收获**：大规模系统的核心挑战不是算法，而是「如何在数千台机器上协调、容错、演进」。Jeff Dean 用 Google 的真实数据（搜索延迟、索引规模、故障率）展示了「规模如何改变一切」。
- **核心观点**：
  - 延迟数字：Google 搜索的 P99 延迟预算只有几百毫秒，每个组件的延迟都必须严格控制
  - 故障是常态：在 Google 的规模下，每天都有机器挂掉，系统必须假设故障会发生
  - 简单性 > 聪明：MapReduce 之所以成功，不是因为算法精妙，而是因为编程模型简单到任何人都能用
  - 数据驱动决策：所有架构决策都基于真实的性能数据，而非直觉
- **为什么必看**：Jeff Dean 是极少数「既设计了改变世界的系统，又能清晰讲述设计过程」的人。这个演讲是理解「超大规模系统设计」的最佳入口。
- **观看建议**：重点记住他提到的具体数字（延迟、吞吐量、故障率），这些数字会校准你对「规模」的直觉。
- **链接**：YouTube 搜索 "Jeff Dean Building Software Systems at Google"

### 5. The Art of Code Comments / Clean Code Talks

- **演讲者**：Miško Hevery（Angular 创始人，前 Google）
- **年份**：2008-2009（Google Tech Talks 系列）
- **时长**：每个 50-60 分钟
- **一句话收获**：代码的可测试性是可设计性的最佳代理指标。如果你的代码难以测试，不是测试的问题，是设计的问题。
- **核心观点**：
  - 依赖注入不是「框架」，是「设计原则」
  - 全局状态和单例是测试的敌人，也是设计的敌人
  - 「new」关键字是依赖关系的声明，滥用 new = 硬编码依赖
  - 好的代码结构让测试变得显而易见
- **为什么必看**：这个系列是 Google 内部工程师培训的公开版本，影响了整整一代工程师对「可测试代码」的理解。即使你不用 Java/Angular，其中的设计原则完全通用。
- **链接**：YouTube 搜索 "Google Clean Code Talks"

### 6. Turning the Database Inside Out

- **演讲者**：Martin Kleppmann（《Designing Data-Intensive Applications》作者）
- **年份**：2015（Strange Loop）
- **时长**：56 分钟
- **一句话收获**：数据库、消息队列、缓存、搜索引擎……这些看似不同的系统，本质上都是「数据在不同表示形式之间的转换」。理解这个统一视角，你就理解了数据系统设计的本质。
- **核心观点**：
  - 数据库 = 写入时做的工作（索引）+ 读取时做的工作（查询）
  - 日志（log）是所有数据系统的统一抽象
  - 物化视图、CDC、事件溯源都是同一个思想的不同应用
  - 「把数据库翻过来」= 以日志为中心，而非以表为中心
- **为什么必看**：如果你读过 DDIA（《数据密集型应用系统设计》），这个演讲是它的「精华浓缩版」。如果你没读过，这个演讲是最好的「预告片」。
- **链接**：YouTube 搜索 "Martin Kleppmann Turning the Database Inside Out"

## 三、AI / 深度学习

这些演讲帮你建立对 AI 的「第一性原理」理解，而非停留在「调用 API」的层面。

### 7. Let's build GPT: from scratch, in code, spelled out

- **演讲者**：Andrej Karpathy（前 Tesla AI 总监，OpenAI 创始成员）
- **年份**：2023（YouTube）
- **时长**：1 小时 57 分钟
- **一句话收获**：从零开始、逐行代码实现一个 GPT 模型。看完之后，「Transformer」「注意力机制」「自回归生成」不再是黑箱，而是你能在纸上画出来的东西。
- **核心观点**：
  - GPT 的核心就是：Token Embedding → Self-Attention → FFN → 重复 N 层 → 预测下一个 token
  - 注意力机制的本质是「加权平均」：每个 token 看所有其他 token，决定「关注谁」
  - 训练就是「让模型预测下一个 token 的概率分布尽可能接近真实分布」
  - 整个 GPT-2 级别的模型，300 行 PyTorch 就能实现
- **为什么必看**：这是互联网上最好的「从零理解 GPT」教程，没有之一。Karpathy 的教学能力是顶级的——他能把最复杂的概念用最简单的代码和类比讲清楚。即使你不做 AI 研究，理解 GPT 的工作原理也是 2024+ 每个工程师的基本素养。
- **观看建议**：建议边看边跟着写代码。如果 2 小时太长，至少看完前 60 分钟（到 Multi-Head Attention 实现完毕）。
- **链接**：YouTube 搜索 "Andrej Karpathy Let's build GPT"

### 8. Neural Networks: Zero to Hero（系列）

- **演讲者**：Andrej Karpathy
- **年份**：2022-2024（YouTube 系列）
- **时长**：每个 1.5-2.5 小时，共 8 集
- **一句话收获**：从最基础的反向传播开始，逐步构建到完整的语言模型。这是「从零到一理解深度学习」最完整的免费课程。
- **核心观点**：
  - 神经网络就是「可微分的计算图」+ 「链式法则求梯度」
  - 反向传播不神秘，就是微积分的链式法则
  - 从 bigram 模型 → MLP → RNN → Transformer，每一步都是在前一步基础上加一个组件
  - 理解「为什么」比「怎么调参」重要 100 倍
- **为什么必看**：如果你想真正理解 AI（而不是只会调 API），这个系列是最佳起点。Karpathy 把「从高中数学到 Transformer」的路径铺得极其平滑。
- **链接**：YouTube 搜索 "Andrej Karpathy Neural Networks Zero to Hero"

### 9. Deep Learning（系列讲座）

- **演讲者**：Geoffrey Hinton（深度学习之父，2024 诺贝尔物理学奖得主）
- **年份**：2012-2021（多次讲座，推荐 2021 年 Microsoft Research 版本）
- **时长**：每次 60-90 分钟
- **一句话收获**：从「为什么神经网络曾经被抛弃」到「为什么它最终成功了」，Hinton 用亲历者的视角讲述了深度学习 50 年的起伏。
- **核心观点**：
  - 神经网络的核心思想：用大量简单的「神经元」通过连接权重来学习表示
  - 反向传播 + 大数据 + GPU = 深度学习的三大支柱
  - 「胶囊网络」的构想：用「部分-整体」关系替代池化，保留空间信息
  - AI 的未来不是更大的模型，而是更好的学习算法（少样本学习、无监督学习）
- **为什么必看**：Hinton 是深度学习的「教父」。听他讲 AI，就像听爱因斯坦讲相对论的历史。他的直觉和远见（很多在 20 年前提出，后来被验证）是理解 AI 发展方向的最佳指南。
- **链接**：YouTube 搜索 "Geoffrey Hinton Deep Learning lecture"

## 四、创业 / 产品思维

技术人不能只懂技术。这些演讲帮你理解「技术如何变成产品、产品如何变成商业」。

### 10. 微信公开课：张小龙演讲

- **演讲者**：张小龙（微信之父，腾讯高级副总裁）
- **年份**：2016 / 2018 / 2019 / 2021（微信公开课 PRO）
- **时长**：60-120 分钟（每年不同）
- **一句话收获**：好的产品是「用完即走」的。技术的终极价值不是炫技，而是「让人的生活更简单」。
- **核心观点**：
  - 「好的产品是用完即走的」——不要试图占用用户时间
  - 「我们不做用户调研，我们观察用户行为」
  - 「小程序的本质是：让服务触手可及，但无需安装」
  - 「克制是一种能力」：微信拒绝了很多「看起来能赚钱但伤害体验」的功能
  - 技术人的产品思维：不是「我能做什么」，而是「用户需要什么，我如何用技术最优雅地满足」
- **为什么必看**：张小龙是中国最成功的「技术人做产品」的案例。他的演讲不是产品方法论，而是一种「产品哲学」——关于克制、关于简单、关于尊重用户。对技术人来说，这是理解「技术为谁服务」的最佳教材。
- **观看建议**：推荐 2018 年版本（最完整，覆盖了微信的设计哲学）和 2021 年版本（对视频号和直播的思考）。
- **链接**：微信搜索「微信公开课 张小龙」或 B 站搜索

### 11. 梁文锋：DeepSeek 的技术路线与开源哲学

- **演讲者**：梁文锋（DeepSeek 创始人）
- **年份**：2024-2025（多次公开访谈和技术分享）
- **时长**：30-90 分钟不等
- **一句话收获**：在 AI 大模型领域，「开源 + 极致工程效率 + 正确的技术路线选择」可以让小团队挑战巨头。
- **核心观点**：
  - 技术路线选择比资源堆砌更重要：DeepSeek 选择了 MoE（混合专家）架构，用更少的计算达到更好的效果
  - 开源不是「做慈善」，是「建立生态」：开源让社区帮你验证、改进、传播
  - 中国 AI 团队的核心竞争力不是算力，是「工程效率」和「对应用场景的理解」
  - 小团队的优势：决策快、没有官僚主义、每个人都能影响技术方向
- **为什么必看**：DeepSeek 是 2024-2025 年中国 AI 领域最引人注目的案例。梁文锋的思考代表了一种「技术理想主义 + 工程实用主义」的结合，对中国技术人特别有参考价值。
- **链接**：B 站 / YouTube 搜索 "DeepSeek 梁文锋"

## 五、职业发展

这些演讲帮你思考「技术人的路到底怎么走」。

### 12. Rethinking the Developer Career Path

- **演讲者**：Randall Koutnik（前 Netflix 高级工程师）
- **年份**：2018（O'Reilly Software Architecture Conference）
- **时长**：38 分钟
- **一句话收获**：开发者的职业路径不是「初级 → 高级 → 架构师 → 经理」的线性阶梯，而是「执行者 → 解决问题者 → 定义问题者」的认知跃迁。
- **核心观点**：
  - 初级工程师：被给予明确的问题，执行解决方案
  - 高级工程师：发现并定义问题，设计解决方案
  - Staff/Principal：定义「什么问题值得解决」，影响整个组织的技术方向
  - 大多数「职业焦虑」来自用错误的标尺衡量自己：用「写了多少代码」衡量一个应该「定义问题」的人
  - 晋升不是「做更多同样的事」，而是「做不同层次的事」
- **为什么必看**：这是过去 10 年最清晰的「技术人职业发展框架」。它帮你理解「为什么我写了 5 年代码还是高级」「为什么有些人 3 年就晋升了」。答案不在代码量，在认知层次。
- **观看建议**：只有 38 分钟，建议一次看完。重点记住「执行者 → 解决问题者 → 定义问题者」这个框架。
- **链接**：YouTube 搜索 "Randall Koutnik Rethinking Developer Career Path"

### 13. The Myth of the Genius Programmer

- **演讲者**：Brian Fitzpatrick, Ben Collins-Sussman（Google 工程师，《Team Geek》作者）
- **年份**：2009（OSCON）
- **时长**：55 分钟
- **一句话收获**：「天才程序员」是一个有害的神话。真正优秀的工程师靠的是「谦逊、尊重、信任」（HRT），而不是「独自一人在地下室写出完美代码」。
- **核心观点**：
  - 「天才神话」让程序员害怕暴露自己的不足，导致不求助、不分享、不协作
  - 好的工程师不是「什么都知道」，而是「快速学习 + 有效协作」
  - 代码 Review 不是「找茬」，是「集体智慧」
  - 脆弱性（vulnerability）是信任的基础：承认「我不知道」比假装知道更有力量
- **为什么必看**：如果你曾经因为「问了一个蠢问题」而羞耻，或者因为「代码被别人 review」而焦虑，这个演讲会治愈你。它重新定义了「优秀工程师」的标准：不是智商，是协作能力。
- **链接**：YouTube 搜索 "Myth of the Genius Programmer"

### 14. How to Do Great Work

- **演讲者**：Paul Graham（Y Combinator 创始人）
- **年份**：2023（文章 + 多次演讲版本）
- **时长**：45-60 分钟
- **一句话收获**：做出伟大工作需要四个要素：选择正确的领域、足够的好奇心、大量的刻意练习、以及「允许自己走弯路」的勇气。
- **核心观点**：
  - 选择比努力重要：在一个你不感兴趣的领域，你永远做不到极致
  - 好奇心是最好的指南针：跟着「这真有趣」走，而不是跟着「这很热门」走
  - 伟大工作不是线性的：你需要大量的「看似无用的探索」才能找到真正的突破点
  - 不要等到「准备好了」才开始：做的过程中才能学会
- **为什么必看**：Paul Graham 的思考深度和表达能力是顶级的。这个演讲/文章不只适用于创业，适用于任何「想在某个领域做到极致」的人。
- **链接**：搜索 "Paul Graham How to Do Great Work"

## 六、DevOps / 工程文化

这些演讲帮你理解「如何让团队持续、安全、快速地交付软件」。

### 15. The Phoenix Project / DevOps 系列演讲

- **演讲者**：Gene Kim（《凤凰项目》《独角兽项目》作者）
- **年份**：2013-2023（多次 DevOps Enterprise Summit 演讲）
- **时长**：45-60 分钟
- **一句话收获**：DevOps 不是「开发 + 运维合并」，而是「用系统思维消除从代码到生产之间的所有浪费和等待」。
- **核心观点**：
  - 三步工作法：① 从左到右的流动（消除瓶颈）② 从右到左的反馈（快速发现问题）③ 持续实验和学习
  - 部署频率和稳定性不是矛盾的：高频率部署反而降低风险（小批量 = 小爆炸半径）
  - 技术债是「向未来借时间」，不还会破产
  - 文化 > 工具：没有信任和协作文化，再好的 CI/CD 工具也没用
- **为什么必看**：Gene Kim 把 DevOps 从「一堆工具」提升到了「组织哲学」的高度。如果你在一个「开发扔给运维、运维骂开发」的环境里工作，这些演讲会帮你理解问题的根源和解决方向。
- **链接**：YouTube 搜索 "Gene Kim DevOps Enterprise Summit"

### 16. Blameless PostMortems and the Just Culture

- **演讲者**：John Allspaw（前 Etsy CTO，Adaptive Capacity Labs 创始人）
- **年份**：2012-2016（多次演讲）
- **时长**：40-55 分钟
- **一句话收获**：事故复盘的目的不是「找到谁犯了错」，而是「理解为什么在那个时刻，那个人的行为在他看来是合理的」。
- **核心观点**：
  - 「人因错误」几乎从来不是根因，而是系统设计的症状
  - 惩罚犯错的人 = 鼓励隐瞒 = 下次更大的事故
  - 「Just Culture」：区分「诚实的错误」「冒险行为」「故意破坏」，只对后两者追责
  - 复盘的核心问题不是「谁做的」，而是「什么条件让这个行为变得合理」
- **为什么必看**：如果你的团队在出事故后第一反应是「谁干的」，这个演讲会改变整个团队的文化。它不只适用于 DevOps，适用于任何需要「从失败中学习」的组织。
- **链接**：YouTube 搜索 "John Allspaw Blameless PostMortem"

## 七、中国技术人的声音

### 17. 左耳朵耗子（陈皓）：技术人的职业素养

- **演讲者**：陈皓（左耳朵耗子，MegaEase 创始人，已故）
- **年份**：2017-2022（多次 QCon / ArchSummit 演讲）
- **时长**：45-60 分钟
- **一句话收获**：技术人的核心竞争力不是「会用什么框架」，而是「底层基础 + 学习能力 + 工程素养」。追逐热点是焦虑，打好基础是自由。
- **核心观点**：
  - 「不要做 CRUD 工程师」：要理解你用的每个工具背后的原理
  - 「技术领导力」不是管理，是「用技术判断力影响决策」
  - 学习的方法：读源码、读论文、造轮子、写文章
  - 程序员的价值 = 解决问题的能力 × 影响范围
- **为什么必看**：陈皓是中国技术圈最具影响力的「技术布道者」之一。他的演讲直接、犀利、不灌鸡汤，是「中国程序员应该如何思考」的最佳参考。
- **链接**：B 站 / YouTube 搜索 "左耳朵耗子 演讲" 或 "陈皓 QCon"

### 18. 尤雨溪：Vue.js 的设计哲学

- **演讲者**：尤雨溪（Evan You，Vue.js 创始人）
- **年份**：2016-2024（多次 VueConf / JSConf 演讲）
- **时长**：30-50 分钟
- **一句话收获**：好的框架设计不是「功能最多」，而是「在正确的抽象层次上，让最常见的事情最简单」。
- **核心观点**：
  - 渐进式（Progressive）：你可以只用 Vue 的一小部分，也可以用它的全部
  - 模板 vs JSX：不是对错问题，是「目标用户是谁」的问题
  - 框架设计的核心权衡：灵活性 vs 约束、性能 vs 开发体验、简单 vs 强大
  - 独立开发者的生存之道：开源 + 赞助 + 咨询，不依赖单一公司
- **为什么必看**：尤雨溪是「中国技术人在全球开源社区最成功的案例」之一。他的演讲不只关于 Vue，更关于「如何设计一个被百万人使用的工具」和「如何作为独立开发者生存」。
- **链接**：YouTube 搜索 "Evan You Vue.js talk"

## 按职业阶段的观看路径

### 0-3 年：建立正确认知（选 4 个）

1. **Simple Made Easy**（理解什么是好设计）
2. **Myth of the Genius Programmer**（消除「我不够聪明」的焦虑）
3. **Let's build GPT**（理解 AI 时代的基础）
4. **Rethinking Developer Career Path**（建立正确的成长预期）

### 3-7 年：深化系统思维（选 6 个）

在基础 4 个之上，加：
5. **Building Software Systems at Google**（理解规模）
6. **Turning the Database Inside Out**（理解数据系统）
7. **Inventing on Principle**（重新想象编程）
8. **张小龙微信公开课**（理解产品思维）
9. **Gene Kim DevOps**（理解交付系统）

- 这个观点在我的场景中是否成立？
- 这个思维模型如何应用到我当前的团队/系统中？
- 我能否做一次自己的演讲，把这些思想本地化？

## 从「看演讲」到「做演讲」

看完这些演讲后，最好的学习方式是**自己也做一次**。

- 选一个你最近解决的技术问题，做一次 15 分钟的团队内分享
- 把你看过的 3 个演讲的核心思想，用你自己的话写成一篇博客
- 参加一次本地的技术 Meetup，做一次 20-30 分钟的演讲

详细的演讲方法论，参见 [[如何做技术演讲]]。
