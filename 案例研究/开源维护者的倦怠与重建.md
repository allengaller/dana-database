# 开源维护者的倦怠与重建

> 「我每周花 40 小时在开源项目上，没有报酬，没有假期，收到的只有抱怨和催促。有一天早上我打开 GitHub，看到 47 个新 issue，我的第一反应不是兴奋，而是恶心。我知道我完了。」
> —— 一位匿名开源维护者，2023 年

> 开源软件支撑着现代互联网的 90% 以上基础设施，但维护它的人正在一个接一个地崩溃。这不是个人问题，这是系统性问题。
> —— Nadia Eghbal,《Roads and Bridges》(2016)

---

## 背景

**人物**：化名「林远」，男，32 岁，某中型互联网公司高级后端工程师。

**项目**：一个 Node.js 生态的数据验证与序列化库（化名 `validify`），GitHub 12k stars，npm 周下载量 200 万次，被 3000+ 个项目依赖。

**阶段**：林远在 2019 年（工作第 2 年）创建了 `validify`，最初是为了解决自己项目中的一个痛点——现有的验证库要么太重（zod 当时还不流行），要么 API 设计不优雅。他花了一个周末写了第一版，发到 GitHub 上。

**发展轨迹**：
- 2019 年：发布 v0.1，最初只有 20 个 star，主要是朋友和同事在用
- 2020 年：被一个知名框架选为默认验证方案，star 数从 200 暴涨到 5000
- 2021 年：npm 周下载量突破 50 万，issue 和 PR 开始涌入
- 2022 年：star 破万，npm 周下载量 200 万，成为该领域事实标准之一
- 2023 年初：林远开始感到明显的倦怠

**约束条件**：
- 全职工作 996（公司正在冲刺上市），每天工作 10-12 小时
- 开源维护完全利用业余时间——晚上 10 点到凌晨 1 点，周末
- 没有共同维护者（co-maintainer），所有决策和代码审查都是他一个人
- 没有企业赞助，唯一的收入来源是 GitHub Sponsors（每月约 $200）
- 已婚，有一个 1 岁的孩子

**当时的状态**：到 2023 年初，林远每周花 15-20 小时在 `validify` 上——处理 issue、review PR、写文档、发布新版本、回应安全漏洞报告。这几乎占据了他所有的业余时间。他的妻子抱怨他「永远在电脑前」，他的身体开始出现颈椎和睡眠问题，他在公司的工作表现也开始下滑。

---

## 挑战与困境

### 困境一：无限的需求 vs 有限的时间

`validify` 的 issue tracker 在 2023 年初有 180+ 个 open issues。其中：
- 约 30% 是功能请求（「能不能支持 X 格式？」「能不能加 Y 特性？」）
- 约 25% 是 bug 报告（其中约一半是用户误用，不是真正的 bug）
- 约 20% 是问题/讨论（「这个 API 为什么这样设计？」「怎么实现 Z？」）
- 约 15% 是 PR（需要 review 和合并）
- 约 10% 是安全相关（需要紧急处理）

每天打开 GitHub，林远面对的是 5-10 个新 issue + 2-3 个新 PR。每个 issue 平均需要 15-30 分钟来理解、复现、回复。每个 PR 需要 30-60 分钟来 review。

**关键数字**：即使他每周投入 20 小时，也只能处理新增需求的一半。backlog 持续增长。

### 困境二：情感劳动的隐形成本

开源维护者面临的大量工作不是「写代码」，而是**情感劳动**：

- **不合理的期望**：「这个 bug 影响了我公司的生产环境，你必须今天修！」（一个免费开源项目）
- ** entitlement（权利感）**：「我用了你的库，你就有义务支持我的用例」
- **攻击性沟通**：「这个 API 设计是垃圾，你是不是不会写代码？」
- **道德绑架**：「如果你不维护了，3000 个项目都会受影响，你负得起这个责任吗？」
- **无休止的解释**：同一个问题被不同人反复问，每次都要耐心回答

林远后来在博客中写道：「最消耗我的不是写代码，而是每天面对 10 个陌生人的期望、抱怨和偶尔的恶意。我变成了一个免费的、24/7 的客服。」

### 困境三：身份认同的绑架

到 2022 年底，`validify` 已经不仅仅是一个项目——它变成了林远的**身份**。

- 他的 GitHub profile 是他在技术社区的「名片」
- 他因为 `validify` 被邀请做技术演讲、写技术文章
- 他的职业声誉与项目深度绑定
- 他害怕「如果我不维护了，别人会怎么看我？」

这种身份绑架让他无法放手。即使身心俱疲，他仍然觉得「我不能停下来」。

### 困境四：「公地悲剧」的结构性问题

`validify` 的困境不是个案，而是开源生态的结构性问题：

- **使用者众多，贡献者稀少**：200 万周下载量，但活跃贡献者只有 3-5 人（包括林远自己）
- **企业搭便车**：多家上市公司在生产环境使用 `validify`，但没有一家提供赞助或贡献工程师时间
- **维护者无报酬**：林远每月从 GitHub Sponsors 获得约 $200，相当于每小时 $2-3（远低于他的市场工资）
- **没有退出机制**：如果他突然停止维护，3000 个依赖项目会受影响，但他没有任何「交接」的基础设施

Nadia Eghbal 在《Roads and Bridges》中将此比喻为：「我们建造了价值数十亿的数字基础设施，然后把它交给志愿者维护，不给他们任何报酬或支持，还期望他们永远不要抱怨。」

## 关键决策与转折

### 转折点：2023 年 3 月的「崩溃事件」

2023 年 3 月的一个周六凌晨 1 点，林远在 review 第 7 个 PR 时，一个用户在一个 issue 下评论：「这个 bug 已经报了 3 周了，维护者是不是已经放弃这个项目了？如果不想维护就明确说，别浪费大家时间。」

这条评论本身并不过分——3 周确实很长。但在那个时刻，它成为了压垮骆驼的最后一根稻草。林远后来描述：

> 「我突然感到一阵强烈的愤怒，然后是深深的无力感。我想关掉电脑，想删掉整个仓库，想发一条'我不干了'的声明。我坐在电脑前发了 20 分钟呆，然后去卫生间吐了。」

第二天，他没有打开电脑。接下来的一周，他都没有碰 `validify`。这是他 4 年来第一次完全断开与项目的连接。

### 决策一：承认问题，寻求帮助

一周后，林远做了一件他之前一直拒绝做的事：**他在 Twitter 上发了一条脆弱的帖子**。

> 「最近状态很差。validify 的维护已经严重影响了我的健康和家庭生活。我需要认真思考接下来怎么办。如果你依赖这个项目，请理解我也是一个有极限的人。」

这条帖子获得了 800+ 个 like 和 200+ 条回复。让他意外的是，绝大多数回复是支持和理解，而非指责。多位开源维护者私信他分享了自己的类似经历。

**关键洞见**：他之前一直假设「如果我表达疲惫，社区会指责我不负责任」。实际上，大多数人是理解的——他们只是不知道维护者的真实状态。**沉默让问题恶化，表达是恢复的第一步。**

### 决策二：建立边界

林远花了两周时间思考，然后做了一系列具体的边界设定：

1. **设定响应时间期望**：在 README 中明确写道：「维护者是兼职志愿者。Issue 响应时间为 2-4 周，PR review 为 1-2 周。紧急问题请考虑付费支持或自行 fork。」

2. **关闭「即时响应」通道**：不再在手机上安装 GitHub 通知。只在固定的时间（周三和周六晚上）处理 issue 和 PR。

3. **引入 issue 模板和自动化**：
   - 强制使用 bug report 模板（必须包含复现步骤）
   - 用 GitHub Actions 自动关闭不符合模板的 issue
   - 用 bot 自动标记 stale issues（60 天无活动自动关闭）

4. **学会说「不」**：对不合理的功能请求，标准回复：「这个需求超出了项目的核心范围。建议你 fork 并自行实现，或者考虑其他库。」不再试图让所有人满意。

5. **保护个人时间**：晚上 10 点后不碰开源项目。周末只投入最多 4 小时。

### 决策三：寻找共同维护者

这是最关键也最困难的一步。林远花了 3 个月时间寻找和培养共同维护者：

**第一步：识别潜在贡献者**
- 查看过去 6 个月提交过高质量 PR 的用户
- 查看在 issue 中经常帮助他人回答问题的用户
- 在 Twitter/社区中公开招募

**第二步：渐进式授权**
- 先给 2 个活跃贡献者「triage」权限（可以标记和关闭 issue）
- 观察 1 个月后，给 1 个人「write」权限（可以合并 PR）
- 最终确定了 2 个共同维护者，分担代码 review 和 issue 处理

**第三步：文档化决策权**
- 写了 CONTRIBUTING.md 和 GOVERNANCE.md
- 明确了什么决策需要林远参与（breaking changes、核心 API 设计），什么可以由共同维护者决定（bug fix、文档改进）
- 建立了维护者之间的异步沟通渠道（一个小的 Discord server）

### 决策四：探索可持续模式

林远开始认真思考开源项目的可持续性问题：

1. **GitHub Sponsors 升级**：设置了更清晰的赞助层级，明确说明赞助金额对应什么（$10 = 感谢，$100 = 优先 issue 响应，$500 = 季度技术咨询）

2. **企业赞助**：主动联系了 5 家使用 `validify` 的上市公司，其中 2 家同意每年赞助 $5000-$10000

3. **Open Collective**：建立了透明的财务账户，所有收入支出公开

4. **考虑基金会托管**：与 OpenJS Foundation 接触，讨论将项目转移到基金会下的可能性（最终因为项目规模还不够大而暂缓）

**结果**：到 2023 年底，月收入从 $200 增加到约 $1500。虽然仍然远低于市场工资，但足以覆盖一些基础设施成本（CI、域名、文档托管），更重要的是，它传递了一个信号：「你的工作是被认可和重视的。」

## 结果与复盘

### 量化结果

| 指标 | 崩溃前（2023.01） | 恢复后（2024.06） |
|------|-------------------|-------------------|
| 周投入时间 | 15-20 小时 | 5-8 小时 |
| Open issues | 180+ | 40-60（健康范围） |
| Issue 平均响应时间 | 3 周（且不稳定） | 1-2 周（稳定） |
| 维护者数量 | 1 | 3 |
| 月收入 | $200 | $1500 |
| 睡眠质量 | 差（经常失眠） | 正常 |
| 家庭关系 | 紧张 | 恢复 |
| 对项目的感受 | 厌恶、义务感 | 重新享受 |

### 什么有效

1. **公开表达脆弱**：打破了「维护者必须永远坚强」的幻觉，获得了社区支持
2. **设定明确边界**：让社区知道维护者是人，有极限
3. **自动化低价值工作**：stale bot + issue 模板减少了 40% 的无效交互
4. **渐进式授权**：不是一次性「找人接手」，而是逐步培养和信任
5. **探索可持续模式**：虽然金额不大，但经济认可对心理有巨大影响

### 什么无效 / 可以做得更好

1. **太晚寻求帮助**：如果在 2021 年（问题刚出现时）就开始寻找共同维护者，可以避免 2 年的痛苦
2. **没有一开始就设定边界**：项目早期「来者不拒」的态度培养了社区的不合理期望
3. **过度依赖单一维护者**：项目治理结构从一开始就应该考虑多人协作
4. **忽视身体信号**：颈椎问题、失眠、恶心——这些信号出现时就应该立即行动，而非「再坚持一下」

### 与真实案例的对照

林远的经历是多个真实案例的复合：

- **Marak Squires（faker.js / colors.js）**：2022 年 1 月，Marak 在 faker.js 中故意插入破坏性代码，表达对企业「白嫖」开源的不满。这是一个更极端的「崩溃」——不是安静地退出，而是破坏性地退出。林远的选择（设定边界、寻找共同维护者）是更健康的替代路径。

- **core-js 维护者（Denis Pushkarev）**：core-js 是 JavaScript 最基础的 polyfill 库，被几乎所有前端项目依赖。Denis 在 2019 年入狱 18 个月（交通事故），出狱后发现自己无法找到工作，同时 core-js 的维护负担巨大。他在 2023 年公开呼吁经济支持，揭示了「关键基础设施由一个人维护」的脆弱性。

- **Vue.js / 尤雨溪（Evan You）**：Vue.js 是一个正面案例。尤雨溪在 Vue 2 到 Vue 3 的过渡期，有意识地建立了核心团队（core team），将维护工作分散到多人。Vue 的治理模式（核心团队 + 社区贡献者 + 企业赞助）是可持续开源的典范。参见 [[尤雨溪]]。

- **Linus Torvalds / Linux**：Linus 是另一个正面案例——他从不试图自己做所有事。Linux 内核有数百个维护者，每个子系统有专门的 maintainer。Linus 的角色是「最终仲裁者」而非「唯一贡献者」。参见 [[Linus Torvalds]]。

## 可迁移的经验

### 对开源维护者

1. **从第一天就设计可持续性**：不要等到 burnout 才想「我应该找人帮忙」。在项目早期就写 CONTRIBUTING.md、设定响应时间期望、考虑治理结构。

2. **边界不是自私，是生存**：说「不」、设定响应时间、关闭通知——这些不是「不负责任」，而是确保你能长期维护的前提。一个设定了边界但坚持 5 年的维护者，远胜于一个「来者不拒」但 2 年就崩溃的维护者。

3. **你的价值不等于你的项目**：即使项目停止维护，你作为工程师的价值不会减少。不要让项目成为你唯一的身份认同。

4. **自动化一切可以自动化的**：CI/CD、issue 模板、stale bot、自动标签——每减少 1 小时的手动工作，你就多了 1 小时做高价值决策。

5. **经济可持续性不是「卖灵魂」**：接受赞助、企业支持、甚至商业化，不意味着你「背叛了开源精神」。没有经济基础的开源是不可持续的。

### 对开源使用者

1. **你是受益者，不是客户**：免费开源软件不是产品，维护者不是你的客服。用尊重和感激的态度沟通。

2. **贡献不只是代码**：回答 issue 中的问题、改进文档、帮助新人——这些都是有价值的贡献，不需要写代码。

3. **如果你的公司依赖开源，赞助它**：每年 $5000 的赞助对你的公司是零头，对维护者可能是「继续 vs 放弃」的区别。

4. **不要只是索取**：如果你从项目中受益，考虑回馈——哪怕是 star、tweet、或者在 issue 中说一句「谢谢」。

### 对技术管理者

1. **允许工程师在工作时间贡献开源**：如果你的产品依赖某个开源项目，让工程师在工作时间修复 bug、贡献代码，是成本最低的「赞助」。

2. **关注团队成员的开源负担**：如果你的团队成员在维护知名开源项目，注意他们是否过载。考虑在工作量上给予调整。

3. **将开源贡献纳入绩效评估**：维护一个被广泛使用的开源项目，其影响力可能超过内部项目。这应该被认可。

### 对所有人：识别倦怠的早期信号

| 信号 | 含义 | 行动 |
|------|------|------|
| 打开项目时感到焦虑而非兴奋 | 情感耗竭开始 | 立即减少投入，休息 1-2 周 |
| 开始厌恶用户/社区 | 共情疲劳 | 设定边界，减少直接交互 |
| 「再坚持一下就好了」的想法 | 否认问题 | 认真评估是否需要结构性改变 |
| 身体症状（失眠、颈椎、头痛） | 身体在发出警告 | 这不是「意志力」问题，是健康危机 |
| 影响工作和家庭 | 问题已经溢出 | 必须立即行动，不能继续忽视 |
