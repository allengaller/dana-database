# 开源维护者的燃烧与重生

> 「有一天晚上 11 点半，我在回复第 47 个 issue。那个人说'这个 bug 你三天了还没修，你到底行不行？'
> 我突然意识到，我已经连续 6 个月没有一天是在 12 点前睡觉的了。
> 而我的本职工作绩效，已经滑到了团队倒数。」

---

## 背景

**人物**：化名「老何」，男，某二线城市互联网公司高级后端工程师。

**阶段**：工作第 9 年，在一家中型 SaaS 公司担任后端技术负责人，带 8 人团队。

**开源项目**：一个 Go 语言的轻量级任务调度框架（化名「GoTasker」），GitHub 5,200+ stars，被数百个项目使用。

**约束条件**：

- 985 本科，计算机专业，Go 语言深度使用者
- 本职工作 996（早 9 晚 9 一周 6 天），通勤单程 45 分钟
- 已婚，有一个 4 岁的女儿
- GoTasker 是他唯一的开源项目，从第 3 年开始维护，到崩溃时已维护 6 年
- 项目有 3 个 GitHub Sponsors（每月共 $150），无企业赞助
- 无共同维护者，所有 issue、PR、release 都是他一个人处理

**当时的状态**：老何在 Go 社区有一定知名度，GoTasker 是他最引以为傲的作品。每次技术面试，面试官都会提到这个项目。他觉得自己「有义务」维护好它——毕竟 5000 多个人 star 了它，数百个生产系统在依赖它。

---

## 燃烧过程：六年是怎么一步步走到崩溃的

### 第一阶段：热情期（第 1-2 年）

GoTasker 诞生于老何工作中的一个真实痛点：现有的任务调度框架太重，他需要一个轻量的、Go-native 的方案。

- 第 1 年：自己用，顺便开源。偶尔有人提 issue，他很快回复。感觉很好——「有人用我写的东西」。
- 第 2 年：stars 从 50 涨到 800。开始有人提 PR，他认真 review 每一个。周末花 3-4 小时在项目中，感觉是「有意义的爱好」。

**这个阶段的健康信号**：
- 投入时间可控（每周 3-5 小时）
- 有正反馈（stars 增长、感谢评论）
- 不影响本职工作和家庭生活
- 纯粹因为兴趣，没有「义务感」

### 第二阶段：增长期（第 3-4 年）

Stars 突破 2000，GoTasker 开始被一些知名项目引用。

- Issue 数量从每周 2-3 个变成每天 2-3 个
- 开始收到「为什么还不支持 X 功能？」「这个 bug 什么时候修？」的催促
- 有公司开始在生产环境使用，提的 issue 更复杂、更紧急
- 老何开始每天晚上 9 点到家后，花 1-2 小时处理 issue

**关键转折点**：第 3 年某天，一个用户在 issue 中说：「我们在生产环境用了 GoTasker，这个 bug 导致我们丢了客户数据。你能今天修吗？」

老何那天晚上修到凌晨 2 点。修完后他感到一种混合的情绪：自豪（「有人在生产环境用我的东西」）+ 压力（「如果我不修，别人的系统会出问题」）。

**从这一刻起，「爱好」变成了「责任」。**

### 第三阶段：义务期（第 5-6 年）

Stars 突破 5000。GoTasker 成为 Go 生态中任务调度的「事实标准」之一。

**日常变成这样**：

| 时间 | 活动 |
|------|------|
| 9:00-21:00 | 本职工作（996） |
| 21:00-21:45 | 通勤回家 |
| 21:45-22:30 | 陪女儿（经常心不在焉，想着未回的 issue） |
| 22:30-00:30 | 处理 GoTasker：回 issue、review PR、修 bug |
| 00:30-01:00 | 洗漱、刷手机、入睡 |
| 周末 | 原本应该陪家人，但「攒了一周的 issue」需要处理 |

**心理状态的变化**：

- **内疚感**：一天没看 issue 就焦虑——「万一有人提了紧急 bug 呢？」
- **义务感**：「5000 个人 star 了它，我有责任维护」
- **愤怒**：对提「低质量 issue」的人愤怒——「你为什么不先看文档？」
- **孤独**：所有事情都是他一个人做，没有人分担
- **被困感**：想停下来，但觉得「如果我不管了，这个项目就死了，那些依赖它的人怎么办？」

**Sponsor 压力**：

3 个 GitHub Sponsors 每月共 $150。钱不多，但它产生了一种微妙的心理压力：「有人付钱给我了，我是不是应该更积极？」其中一个 sponsor 偶尔会在 issue 中 @ 他：「作为 sponsor，我希望这个功能能优先处理。」

$150/月，换来的是无限的责任感。

### 第四阶段：崩溃（第 6 年末）

**触发事件**：一个周五晚上，老何在公司加班到 10 点。回家后打开 GitHub，看到 12 个新 issue，其中 3 个是「duplicate」（重复问题，文档里已经写了），2 个是「feature request」（他不想做的功能），1 个语气很不客气：「这个 bug 报了一周了，你到底修不修？不修我换别的库了。」

他盯着屏幕看了 5 分钟，然后关掉了笔记本。

**接下来的 3 个月**：

- 第 1 周：完全没打开 GoTasker。感到一种奇怪的轻松。
- 第 2 周：开始内疚。「那些 issue 还在那里……」
- 第 3-4 周：试图打开 GitHub，但一看到 issue 列表就感到焦虑和厌恶。
- 第 2 个月：完全无法写代码——不管是 GoTasker 还是本职工作。坐在电脑前发呆。
- 第 3 个月：请了 2 周年假（告诉公司是「家里有事」），实际上每天在家躺着，什么都不想做。

**诊断**：后来他去看了心理咨询师，被告知是「职业倦怠」（burnout）——不是对本职工作的倦怠，而是对 GoTasker 的倦怠。6 年的无偿劳动、无限的责任感、没有边界、没有认可，最终耗尽了他。

**代价**：
- 本职工作绩效连续两个季度 C（团队 8 人中排第 7）
- 和妻子关系紧张（「你每天回来就对着电脑，女儿都不认你了」）
- 身体健康下降（失眠、颈椎问题、体重增加 15 斤）
- 对编程的热情几乎消失（「我不想再看到一行 Go 代码」）

## 恢复过程：从废墟中重建

### 第一步：承认问题（第 4 个月）

老何做的第一件正确的事是**承认自己出了问题**。

他在一篇私人笔记中写道：

> 「我一直在骗自己说'我热爱开源'。但真相是，我已经不热爱了。我维持它是因为内疚和恐惧——怕别人失望，怕项目死掉，怕被说'不负责任'。但没有人要求我做这些。是我自己把'可以做'变成了'必须做'。」

### 第二步：设定边界（第 4-5 个月）

在心理咨询师的建议下，老何做了几件事：

**1. 在 README 中加了一段话**：

```markdown
## 维护说明

GoTasker 由个人维护者利用业余时间开发。
- Issue 响应时间：1-2 周（不保证更快）
- 不接受紧急修复要求
- Feature request 会被评估，但不承诺实现
- 如果你需要商业级支持，请联系 [商业支持链接]
- 欢迎贡献者！如果你愿意帮忙维护，请提 issue 说明。
```

**2. 关闭了「秒回」的习惯**：

- 卸载了手机上的 GitHub App
- 只在周六上午 10-12 点集中处理 issue
- 工作日晚上的 2 小时还给了家人和自己

**3. 学会说「不」**：

- 对不想做的 feature request：「感谢建议，但这不在项目路线图中。欢迎自己实现并提 PR。」
- 对不客气的 issue：不回复，或简短回复「请提供复现步骤」
- 对 sponsor 的优先要求：「感谢支持，但 issue 按优先级排序，不按 sponsor 排序」

### 第三步：找到共同维护者（第 5-7 个月）

老何在 README 中加了「招募维护者」的说明后，有 4 个人表示感兴趣。最终 2 个人成为了 co-maintainer：

- 一个是在校研究生（有时间、有热情）
- 一个是使用 GoTasker 的某公司工程师（有生产经验、有动力）

**分工**：

| 角色 | 职责 |
|------|------|
| 老何 | 架构决策、重大 bug、release 管理 |
| 维护者 A（研究生） | Issue 分类、文档维护、简单 bug fix |
| 维护者 B（公司工程师） | Code review、feature 评估、企业场景支持 |

**关键原则**：老何不再需要「什么都自己做」。他学会了**委托和信任**。

### 第四步：重新定义项目范围（第 7-9 个月）

老何做了一个重要决策：**冻结 feature，只做维护**。

他在 GitHub 上发了一篇公告：

> 「GoTasker 进入维护模式。核心功能已经稳定，我不会再添加大的新功能。
> 未来的重点是：bug 修复、安全更新、依赖升级。
> 如果你需要新功能，欢迎 fork 或提 PR。
> 这不是放弃，而是让项目进入一个可持续的状态。」

**效果**：
- Issue 数量从每天 2-3 个降到每周 2-3 个
- 心理负担大幅减轻（「我不需要再'发展'它了」）
- 一些用户 fork 出去做了自己的版本（这是好事）
- 项目并没有「死」——它稳定了，继续被使用

### 第五步：找到可持续节奏（第 9 个月至今）

**当前的节奏**：

- 每周投入 GoTasker：2-3 小时（周六上午）
- 每月一次 release（如果有需要修复的 bug）
- 每季度一次依赖升级
- 不再看 issue 通知（由维护者 A 分类后 @ 他需要关注的）
- 本职工作绩效恢复到 B+
- 重新开始在周末陪女儿去公园

**心理状态**：

> 「我现在对 GoTasker 的感觉是'骄傲但不焦虑'。它是我做过的最好的技术作品，但它不是我的全部。我不欠任何人一个即时回复。我维护它是因为我想，不是因为别人期望。」

## 复盘：为什么会走到这一步？

### 根本原因分析

| 层面 | 问题 | 本可以怎么做 |
|------|------|-------------|
| 边界 | 从未设定响应时间预期 | 第一天就在 README 写明「个人项目，不保证响应速度」 |
| 委托 | 6 年都是一个人做 | 在 2000 stars 时就开始招募 co-maintainer |
| 范围 | 不断接受 feature request | 早期就定义「项目做什么、不做什么」 |
| 身份 | 把项目等同于自我价值 | 「GoTasker 是我做的，但我不等于 GoTasker」 |
| 内疚 | 觉得「不回复 = 不负责任」 | 认识到：无偿开源没有「不负责任」一说 |
| 反馈 | 只有负面反馈（issue = 问题） | 主动收集正面反馈（用户感谢、使用案例） |

### 开源维护者的常见心理陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| 救世主情结 | 「只有我能维护这个项目」 | 培养 co-maintainer，写文档让别人能接手 |
| 无限责任 | 「有人用了我的代码，我就必须负责」 | 开源协议（MIT/Apache）明确免责 |
| 身份绑定 | 「如果项目死了，我就失败了」 | 项目有生命周期，结束不等于失败 |
| 比较陷阱 | 「XX 项目有 50K stars，我才 5K」 | 价值不由 star 数定义 |
| 沉没成本 | 「我已经投入 6 年了，不能停」 | 过去的投入不决定未来的选择 |
| 讨好型 | 不敢拒绝任何 feature request | 说「不」是维护者的权利 |

## 给开源维护者的建议

### 预防阶段（项目早期）

1. **从第一天就设定边界**：在 README 中写明维护节奏、响应时间、项目范围
2. **写 CONTRIBUTING.md**：让别人知道怎么贡献，降低你的瓶颈效应
3. **不要追求「让所有人满意」**：你的项目不需要满足所有人的需求
4. **保留「不做清单」**：明确列出项目不会做的事情

### 增长阶段（stars 快速增长时）

5. **尽早招募 co-maintainer**：不要等到 burnout 才找人帮忙
6. **自动化一切**：CI/CD、自动 release、bot 分类 issue
7. **定期「断联」**：每月至少一周完全不看项目
8. **记录正面反馈**：建一个「感谢文件夹」，把用户的感谢存起来，低落时看

### 维护阶段（项目成熟后）

9. **允许项目「稳定」**：不是所有项目都需要持续发展
10. **考虑「毕业」**：如果项目足够成熟，考虑捐给基金会或转交社区
11. **你的健康 > 项目的活跃度**：没有任何开源项目值得你牺牲健康

## 行业视角：这不是个人问题

老何的故事不是个例。开源维护者 burnout 是一个**系统性问题**：

- **2019 年 Tidelift 调查**：58% 的开源维护者表示维护开源是「无偿劳动」，46% 表示「有时感到压力」
- **Nadia Eghbal《Roads and Bridges》**（2016）：系统性地描述了开源基础设施维护者的困境
- **知名案例**：
  - left-pad 事件（2016）：一个 11 行代码的包被删除，半个互联网崩溃
  - core-js 维护者 zloirock：公开表示「我维护着半个互联网的 polyfill，但我付不起房租」
  - [[Mitchell Hashimoto]]（HashiCorp 创始人）：在多个项目中实践了「可持续开源」的模式

**结构性解法**：
- 企业赞助（GitHub Sponsors、Open Collective、Tidelift）
- 基金会支持（Linux Foundation、CNCF、Apache Foundation）
- 维护者带薪（公司允许用工作时间维护开源）
- 社区治理（不让一个人扛所有）

## 立即行动

### 如果你是开源维护者

1. **本周**：在你的项目 README 中加一段「维护说明」，写明响应时间和项目范围。
2. **本月**：评估你的每周投入时间。如果超过 5 小时且没有报酬，认真考虑是否需要缩减范围或找人帮忙。
3. **本季度**：如果你已经感到倦怠，允许自己「暂停」。发一个公告：「维护者休假 2 周，期间不处理 issue。」世界不会因此崩塌。

### 如果你是开源用户

1. **提 issue 前**：先搜索已有 issue，先看文档。不要提「为什么不修 XXX？」这种质问。
2. **表达感谢**：如果你用了别人的开源项目，花 30 秒写一句「谢谢，这个库帮了我大忙」。
3. **贡献回去**：能修 bug 就提 PR，能写文档就写文档。不要只做消费者。

## 与其他心法的连接

- **[[反脆弱与期权思维：让不确定性为你工作]]**：老何的问题是他把自己变成了「单点故障」——项目的反脆弱性为零。找到 co-maintainer、写文档、自动化，都是增加系统反脆弱性的手段。
- **[[能力圈与边界意识]]**：说「不」是能力圈意识的体现。你不需要满足所有人的需求，你只需要做好你选择做的事。
- **[[如何成为技术超级个体]]**：超级个体不是「一个人扛所有」，而是「用杠杆放大自己」。老何后来学会了委托和自动化，这才是真正的超级个体思维。
- **[[Mitchell Hashimoto]]**：HashiCorp 的开源治理模式（BDFL → 社区治理 → 公司支持）是可持续开源的参考。
