### Alan Kay：先画好未来的草图，再把它造出来的人
[[人物志/全球视野/Alan Kay]]

- 不要从"功能"描述，而是从"它是什么媒介"描述
- 例如：不是一个"数据分析后台"，而是一个"让团队看见业务真相的透镜"
- 写一段话，然后问自己：如果这个描述是真的，系统应该有什么变化？
- 打开你负责的某个系统，找一个只是把线下/旧流程数字化的功能
- 问自己：如果利用计算机的动态性和可编程性，这个功能会变成什么样？

### Brendan Eich：10 天发明 JavaScript，半生守护开放 Web 的男人
[[人物志/全球视野/Brendan Eich]]

- 读 Eich 在 JSConf 或 Lex Fridman 播客中关于 JavaScript 起源的访谈
- 重点理解：Scheme 的影响、Self 的影响、为什么它看起来像 Java
- 这会让你对"语言设计妥协"有更现实的认知
- 观察哪些网站加载变快、哪些功能变卡
- 记录你遇到的兼容性问题和心理感受

### Bret Victor：为"看见不可见之物"而发明工具的界面思想家
[[人物志/全球视野/Bret Victor]]

- Bret Victor 的核心原则是"创造者需要即时连接"
- 你所在领域有没有一个类似的、可以指引你多年工作的原则？
- 把这个原则写下来，贴在你能看到的地方
- 不要只用代码或文字描述
- 尝试同时展示：结构、流程、数据变化、关键变量

### Donald Knuth：为了一本完美的书，他发明了一整套排版系统和一门编程范式
[[人物志/全球视野/Donald Knuth]]

- 不需要从第1页开始，也不需要读完
- 随便翻开一页，读一个算法和一个证明
- 重点不是"学会算法"，而是感受**"精确性"是什么滋味**
- 问自己：我的代码有没有达到这种精确度？
- 如果你从未用过，尝试用 Overleaf 写一页技术笔记

### Elon Musk：从自学程序员到重新定义物理边界的工程偏执狂
[[人物志/全球视野/Elon Musk]]

- 选一个你工作中"大家都这么做"的流程/设计/决策
- 问自己："物理上/逻辑上，这真的必须这样吗？如果从头设计，最优解是什么？"
- 写一个500字的分析，发给你的团队或技术社区
- 选一个你想深入但陌生的领域（如分布式系统、编译原理、硬件设计）
- 找到3本该领域被反复引用的经典教材（不是博客、不是短视频）

### Jeff Dean：Google 二十年代分布式系统与 AI 基础设施的灵魂人物
[[人物志/全球视野/Jeff Dean]]

- 读 *MapReduce: Simplified Data Processing on Large Clusters*（OSDI 2004）
- 重点理解：为什么 Map 和 Reduce 是两个函数而不是三个？为什么不需要处理网络分区？
- 在你自己的项目中，找一个"过于复杂的系统"，尝试找到更简单的抽象
- 选一个你维护的服务，计算它的理论性能极限（延迟、吞吐）
- 对比当前实际性能，找出差距最大的环节

### Ken Thompson：Unix之父与四十年的极简工程信仰
[[人物志/全球视野/Ken Thompson]]

- 选一个你团队里"大而全"的模块/服务
- 问自己："这个功能真的需要和系统耦合在一起吗？"
- 尝试把它拆成 2-3 个独立的小工具/服务，用清晰的接口连接
- 记录拆分前后的复杂度变化和测试难度变化
- 选一个你**真正感兴趣**的问题（不是"热门技术"，不是"简历加分项"）

### Kent Beck：TDD、XP 与 JUnit 之父，重新定义"如何写软件"的思想家
[[人物志/全球视野/Kent Beck]]

- 选一个你正在开发的小功能（比如一个工具函数）
- 严格按照"Red → Green → Refactor"循环：
- 先写一个测试，描述期望行为
- 看到测试失败（Red）
- 写最少的代码让测试通过（Green）

### Linus Torvalds：Linux 与 Git 之父，用直率与实用主义统治全球基础设施

### Martin Fowler：用清晰写作定义现代软件架构思想的技术作家
[[人物志/全球视野/Martin Fowler]]

- 读《重构》第二版中的三个常见手法：提取方法（Extract Method）、引入变量（Introduce Variable）、替换条件为多态（Replace Conditional with Polymorphism）

- 体会"小步重构"和"大改一通"的差异
- 格式：上下文 → 决策 → 后果
- 记录"我们考虑过什么方案、为什么选了这个、代价是什么"

### Rob Pike：Unix 哲学的守夜人，用 Go 重新定义软件工程语言的人

### T型深 + 梳型广：技术专家的正确形状
[[心法与原则/T型深 + 梳型广]]

- [ ] **画出你当前的形状**：诚实评估——你是 I 型、T 型还是梳型？你最深的一个领域是什么？在这个领域之外，你有没有「系统性深入」的第二领域？
- [ ] **识别你的核心范式**：你在深耕领域中学到的最核心的 2-3 个思维范式是什么？（例如：「在不确定性中做决策」「用抽象降低复杂度」「在约束条件下寻找最优解」）
- [ ] **选定你的下一个梳齿**：基于核心范式，选一个相邻领域作为下一个系统性深入的方向。不需要今天就开始，但要想清楚方向
- [ ] **在下一个梳齿方向上做一件「真难事」**：不是看几本书，而是参与一个真实项目、解决一个真实问题、产出一个可展示的成果。参考 [[做难事：突破舒适区]]
- [ ] **建立梳齿之间的连接**：写一篇跨领域的文章或做一次分享，把你的主梳齿和新梳齿连接起来。例如：「从分布式系统的视角看前端状态管理」

### 反脆弱与期权思维：让不确定性为你工作
[[心法与原则/反脆弱与期权思维：让不确定性为你工作]]

- [ ] 列出你当前职业的「脆弱点」：如果明天公司倒闭/技术过时/行业萎缩，你会怎样？
- [ ] 购买一张新期权：花 2 小时探索一个你完全不了解的技术方向（如 AI Agent、Rust、WebAssembly）
- [ ] 给一个你欣赏但从未联系过的技术人发一条消息（弱连接期权）
- [ ] 启动一个 side project，用「12 个月 12 个产品」的思路：小、快、可放弃
- [ ] 建立「杠铃学习法」：70% 时间深化核心技能，30% 时间探索前沿

### 复利思维：技术人的指数增长引擎
[[心法与原则/复利思维：技术人的指数增长引擎]]

- [ ] 建立「每周复利存入」习惯：每周至少 1 次高质量输出（博客/PR/分享）
- [ ] 用 [[第二大脑 for 技术人]] 的方法把你的知识显式连接起来，让新学习能连接到旧知识

### 影响力 = 深度 × 持续输出 × 连接
[[心法与原则/影响力 = 深度 × 持续输出 × 连接]]

- [ ] **给你的影响力公式打分**：深度/输出/连接三个因子，各自 1-10 分，你的最短板是哪个？
- [ ] **找到你的「输出锚点」**：选择一个长期输出的形式（博客/周刊/公众号/开源项目），今天发出第一篇
- [ ] **主动连接一位同行**：给你领域里你欣赏但还没有深入交流的一位同行发一条有质量的消息——不是「加个微信」，而是针对他/她的某篇输出给出有深度的反馈
- [ ] **建立持续输出的节奏**：选定一个频率（每周/双周/每月），坚持输出至少一个季度。质量优先于数量，但**频率必须稳定**
- [ ] **参与一个开源社区或技术社区的深度讨论**：不是提一个 issue 就走，而是持续参与一个项目的讨论和贡献，建立在这个社区中的存在感

### 杠杆思维：用最小投入撬动最大产出
[[心法与原则/杠杆思维：用最小投入撬动最大产出]]

- **审计你的时间**：记录一周的时间分配，标记哪些是「线性产出」（做一次就没了），哪些是「杠杆产出」（做一次，持续产生价值）。目标是让杠杆产出占比从 <10% 提升到 20%+。
- **自动化一个重复任务**：找到你每周花 30 分钟以上的重复性工作（部署、数据整理、报告生成），写一个脚本自动化它。这是最小的代码杠杆。
- **写一篇技术文章**：把你最近解决的一个技术问题写成文章，发布到掘金/知乎/个人博客。不需要完美，发出去就是杠杆。
- **评估你的「睡后产出」**：问自己——「如果我明天消失一个月，有什么东西还在为我工作？」如果答案是「没有」，你需要开始构建杠杆。
- **找一个杠杆榜样**：关注一个成功运用杠杆的人（Pieter Levels、阮一峰、尤雨溪），研究他们的杠杆结构，思考哪种模式适合你。

### 概率思维与贝叶斯推理：用概率替代确定性做决策
[[心法与原则/概率思维与贝叶斯推理]]

- [ ] 对一个你「很确定」的判断，刻意寻找 3 条反面证据
- [ ] 建立「预测日志」：每月记录 5 个你对技术/业务/职业的判断及其概率，3 个月后回顾校准度
- [ ] 在下一次技术选型中，使用期望值决策矩阵，而不是「我觉得」

### 第一性原理：从物理层重新推导，而非从类比层复制
[[心法与原则/第一性原理：从基本事实重新推导]]

- [ ] 拿出你最近做的一个技术决策，写下你选它的理由。标记哪些是「验证过的事实」，哪些是「别人都这么做」
- [ ] 找一个你项目中「大家都骂但没人改」的问题，用第一性原理拆解：它的物理/数学约束是什么？最优解和现状差多远？
- [ ] 读 Elon Musk 的 SpaceX 创业故事（Walter Isaacson 传记第 15-20 章），标注他每次用第一性原理的具体时刻
- [ ] 在下一个架构设计中，强制自己先写「基本事实清单」再选方案
- [ ] 建立一个「类比假设审计」习惯：每月审视 1 个团队里的「默认做法」，问「如果今天从零开始，还会这么做吗？」

### 第二层思维：超越显而易见的后果
[[心法与原则/第二层思维：超越显而易见的后果]]

- [ ] 回顾你最近做的一个技术决策，用「然后呢？三连问」分析它的第二层和第三层后果。写下来。
- [ ] 在下一次团队讨论中，当有人说「这样做的好处是 X」时，问一句「然后呢？X 会带来什么新问题？」

- [ ] 建立「决策日志」：每个重大技术决策，记录第一层、第二层、第三层后果的预期，6 个月后回顾哪些预期成真了
- [ ] 对团队正在考虑的一个重大变更（架构迁移、工具链更换等），做一次完整的「利益相关者涟漪图」分析

### 逆向思维：先想怎么失败，再想怎么成功

- [ ] 读 Charlie Munger 的《穷查理宝典》，标注他每次用逆向思维的具体案例

### 遗憾最小化框架：用未来视角做当下选择
[[心法与原则/遗憾最小化框架：用未来视角做当下选择]]

- 写下你一直在犹豫、没有做出的 1-3 个决策
- 它们可能是：要不要换工作、要不要开始一个 side project、要不要学一个新领域、要不要离开一段关系
- 花 10 分钟，闭眼想象 80 岁的自己
- 对每个选项问：「80 岁的我会怎么看？」
- 写下第一反应（不要过度分析）

## 📖 案例研究（真实成长复盘）

### 从技术骨干到创业失败再到技术 VP：一个 CTO 的两年弯路和重建之路
[[案例研究/从技术骨干到创业失败再到技术VP]]

- **在辞职前，先用最小成本验证核心假设**。老周如果当初花 2 个月做一个微信群里的「人肉 SaaS」（手动帮团长开团、收款），就能发现 PMF 不存在，不需要烧 300 万。
- **团队规模永远滞后于业务验证**。在 PMF 之前，3-5 人足够。每多一个人，你的 runway 就短一截。
- **CTO 不是「最厉害的工程师」，是「最懂技术-商业平衡的人」**。如果你从未做过产品决策、从未跟用户聊过天，你还没准备好当 CTO。
- **技术债可以欠，但必须记账**。老周不是不能快速出 MVP，而是他欠了债之后从未还过，最终利息压垮了团队。
- **给自己一个明确的「低谷期」时限**。老周浪费了 5 个月在逃避上。建议：允许自己难过 2-4 周，然后强制启动复盘和求职。

### 从量化金融到AI工程师的跨界
[[案例研究/从量化金融到AI工程师的跨界]]

- 列出你的「可迁移技能清单」。不是「我会 Python」，而是「我理解过拟合的本质，因为我见过它导致真金白银的亏损」。
- 找 3 个已经成功跨界的人聊聊（LinkedIn、脉脉、朋友介绍）。问他们：「你转型时最大的挑战是什么？你希望当时有人告诉你什么？」
- 确定你的「交叉点」：你的旧技能 × 新领域 = 什么独特价值？
- 开始第一个端到端项目。不需要复杂，但必须从数据到部署完整走一遍。
- 找一个目标领域的社区加入（GitHub、Discord、技术群）。开始观察他们怎么说话、怎么思考、关心什么问题。

### 安全工程师的从零到一：一个后端开发者如何用 4 年建成安全团队
[[案例研究/安全工程师的从零到一]]

- **不要从零开始，从你已有的代码开始**。你写了 5 年代码，里面一定有安全问题。去审计自己写过的代码，比看任何教程都有效。阿盾的起点就是修复自己系统里的 7 个漏洞。
- **CTF 是建立攻击直觉的最快方式**。不需要成为 CTF 选手，但坚持打 6 个月 Web 方向的题，你看代码的视角会彻底改变。推荐从 BUUCTF 和 CTFHub 的入门题开始。
- **Bug Bounty 给你真实世界的反馈**。CTF 是靶场，Bug Bounty 是实战。在补天、漏洞盒子、HackerOne 上找目标，哪怕前 3 个月一个洞都挖不到，这个过程本身就在训练你的攻击者思维。
- **选「应用安全」作为开发者的第一个安全方向**。它与你已有的编码能力重叠度最高，学习曲线最平缓。渗透测试、逆向工程可以后续再拓展。
- **「会写代码」是你的核心竞争力，不要丢掉它**。安全行业里大量人不会写代码，只能跑工具。你能读源码、能写 PoC、能开发安全工具——这是「安全 + 开发」的复合优势。参见 [[T型深 + 梳型广]]。

### 开源维护者的燃烧与重生
[[案例研究/开源维护者的燃烧与重生]]

- **本周**：在你的项目 README 中加一段「维护说明」，写明响应时间和项目范围。
- **本月**：评估你的每周投入时间。如果超过 5 小时且没有报酬，认真考虑是否需要缩减范围或找人帮忙。
- **本季度**：如果你已经感到倦怠，允许自己「暂停」。发一个公告：「维护者休假 2 周，期间不处理 issue。」世界不会因此崩塌。
- **提 issue 前**：先搜索已有 issue，先看文档。不要提「为什么不修 XXX？」这种质问。
- **表达感谢**：如果你用了别人的开源项目，花 30 秒写一句「谢谢，这个库帮了我大忙」。
